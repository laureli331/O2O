# V15 运营处理 UI、流程与命名复核及修改建议

日期：2026-10-23（Asia/Shanghai）

实施追记：用户随后要求依本文二次优化，并逐题确认队列、账号目标、能力选择、封禁、限制叠加、整改截止、明确重开及继续共用管理账号；V14/V15本轮不联动。以下保留原评审时点的建议和待确认项，实际选择及实施见[实施记录](v15-ui-flow-implementation-20261023.md)。

文稿状态：本稿同时完成两项工作：

1. 对照 [V14 修改建议](v14-ui-flow-naming-review-20261022.md) 与 [V14 实施记录](v14-ui-flow-implementation-20261022.md)，核对 V15 是否形成一致的运营侧处理闭环。
2. 独立审查 [V15 运营处理预览](http://127.0.0.1:8765/v15.html) 当前的 UI 布局、操作流程、状态逻辑和命名。

本稿只提供可审阅的修改建议，不修改 V15 HTML、CSS、JavaScript、模型、接口或生产业务规则。所有“建议”和“待确认”均不是已经生效的需求；账号权限、处置范围、队列排序、重开规则、真实退款和故障验收仍须以可核实业务及接口事实为准。

## 结论

V15 已经把 V14 中多项关键原则延伸到运营侧：申诉保留原结论上下文，首次回应与最终结论分离，失败、成功和结果未知不混用，结果未知可恢复查询，费用争议只影响对应部分，退款发起不冒充退款成功，操作前有核对步骤。这些是正确方向，建议保留。

当前最需要修正的不是配色或圆角，而是“运营人员能否在提交前准确知道自己正在改什么、影响谁、执行后会变成什么”。实际操作中发现四个高风险缺口：

1. “限制账号”和“封禁账号”只显示举报事项，没有显示将被限制的具体账号、限制能力和影响范围。
2. 费用重算、实收分配、解除处置和故障恢复的核对页只给原则性说明，没有完整呈现执行前后差异或精确分配结果；最终按钮统一叫“确认记录”。
3. 已出结论事项仍显示在“待你处理”标题下，并可直接变回“待补充”，但没有明确的“重新开启处理”动作。
4. 同一套“具体理由＋1/3/7/30天或永久”被复用于不同动作；“永久整改期限”、永久限制与封禁之间的含义不严谨。

推荐采用“**待办与完成分区、动作目标显式、填写过程保留上下文、提交前展示精确前后变化、最终按钮说明结果**”的安全修正方案。第一轮不需要引入人员分工、双人复核、批量处置或 AI 自动判定。

## 1. 审阅与验证范围

### 1.1 已实际检查

- V15-A：8 项正常队列、类型筛选、操作记录、30 项长队列、空队列和加载失败。
- V15-B：举报、申诉、内容巡查、首次回应、请求补充、保持原处置、整改、下架、限制、封禁、解除及事项操作历史。
- V15-C：新材料受理、费用核验、客户欠款异议、注销抵扣、补充通知和 72 小时起点。
- V15-D：实收分配、多收核对、退款发起、成功、失败、结果未知和通道不可用。
- V15-E：故障记录、恢复验收、受影响交易、保护截止和重复事件不续期。
- 结果成功、失败、未知，旧版本冲突，文字草稿，未保存离开保护，错误摘要与字段焦点。
- 320、375、414px 下的标题、胶囊、内容滚动、固定底栏、1000/1001 字边界、减少动态效果和浏览器运行错误。
- 完成申诉核对后返回队列，实际确认“已出结论”卡片仍位于“待你处理”列表末尾。
- 账号限制核对页、费用重算核对页、实收分配核对页和故障恢复核对页的实际可见字段。

### 1.2 已验证为正常，建议保留

- 未登录和普通账号无法读取事项、材料或操作记录。
- 首次回应只记录回应事实，不自动结案。
- 申诉详情展示原结论、原理由和作出时间。
- 操作失败不改状态；结果未知不生成成功记录，并阻止盲目重试。
- 旧版本冲突保留输入，要求重新核对当前版本。
- 费用争议、无争议部分、原标准、原金额和新价格分开呈现。
- 实收只使用已核实支付引用，争议暂缓项不占款，多收与抵扣分开。
- 退款“待核对、待退回、处理中、结果未知、失败、已退回”没有合并成一个成功状态。
- 故障保护限定为已核实范围，保留原有效到期，不因同一事件重放而续期。
- 表单错误摘要、字段错误、草稿、离开保护、焦点循环和减少动态效果工作正常。
- 正常辅助文字对比度已比早期 V14 更清楚，触控目标和轻微按压反馈基本一致。

### 1.3 本次不假定

- 不假定 V15 的“共用管理账号”就是未来生产权限方案。
- 不假定举报对象一定能唯一推导出被限制或封禁的账号。
- 不假定“限制账号”和“封禁账号”的能力范围、对象范围及恢复方式已经确定。
- 不假定所有运营事项都按相同 SLA、风险等级或提交时间排序。
- 不假定已出结论事项可以无条件重新打开，或必须永久不可变。
- 不假定退款、通知、解禁、故障验收和 V14 用户记录已经接入同一服务端。
- 不把评审页外壳中的 A—E 导航、演示状态和操作结果选择器当作正式管理端页面。
- 不用 2026-10-23 的真实日期判断合成事项逾期；页面明确使用固定合成时间，时限判断应基于演示时钟。

## 2. 对照 V14 建议的落实情况

V14 是用户侧通知、举报申诉和处理记录，V15 是运营侧处理台。两者角色和任务不同，不能把 V14 的用户端页面结构直接要求 V15 复刻。以下只核对端到端原则和状态是否一致。

| V14 原则或建议 | V15 当前表现 | 结论 | 后续建议 |
| --- | --- | --- | --- |
| 申诉必须保留原处理对象、结论、理由和时间 | V15 申诉详情展示原结论、原理由和作出时间 | **已对齐** | 表单和核对页也应继续显示必要原上下文，不能只在详情页可见 |
| 首次回应与最终结论分离 | 首次回应是独立动作，记录后仍为处理中 | **已对齐** | 保留；队列排序如采用首次回应目标，需显示剩余或逾期状态 |
| 成功、失败、待确认不得混用 | V15 三种结果分离，未知可恢复查询并阻止重复执行 | **已对齐** | 保留；生产仍需真实幂等、查询和持久化能力 |
| 成功结果应有持久回执和编号 | V15 详情顶部显示操作回执、日志编号和时间 | **已对齐** | 回执标题可由“操作已记录”改为动作结果，例如“原处置已维持” |
| 用户可见状态要区分待处理、处理中和已出结论 | V15 有明确状态，但已出结论卡片仍放在“待你处理”下 | **部分对齐** | 拆成待你处理、等待外部、最近完成或历史记录 |
| 动作名称直接说明结果 | 详情动作较具体，但最终按钮统一为“确认记录” | **部分对齐** | 最终按钮带入动作和关键范围 |
| 申诉从适用原记录进入 | V15 可从具体申诉事项查看原处置 | **已对齐** | V14 与 V15 尚未后台同步，端到端资格与状态只能列为待验证 |
| 服务交付争议与平台费用核验分开 | V15 明确只核验平台佣金，不代追讨或裁判客户债务 | **已对齐** | 保留当前边界说明 |
| 受限材料只展示必要摘要 | V15 材料默认折叠，并说明不恢复地址、联系信息和旧凭据 | **已对齐** | 表单内引用材料时继续最小披露 |
| 提醒设置、个人信息权益和用户通知结构 | V15 不承担这些用户端任务 | **不适用** | 不判为未落实，不在运营台新增相同入口 |
| 待确认状态在用户侧可找回 | V15 只在当前标签页本地合成恢复，且明确不与 V14 同步 | **无法证明端到端** | 后续以真实事务编号和同一状态合同联调验证 |

| --- | --- | --- | --- |
| [Atlassian：About queues in Jira Service Management](https://support.atlassian.com/jira-service-management-cloud/docs/check-out-your-queues/) | 队列用于快速查看和分流事项，通常展示摘要和状态，并按 SLA 或团队目标排序；时钟显示距离下一个目标的时间 | V15 队列增加可解释的排序依据；有真实目标时显示“剩余/已超时”，没有目标的事项不伪造 SLA | 不引入 Jira 的人员分派、项目模型或产品术语 |

以上来源只用于校准队列、核对、危险操作和无障碍原则。V15 仍应沿用本项目米白、低饱和绿色、手机胶囊和克制按压反馈，不复制其它平台的品牌视觉或未确认业务功能。

## 4. 三种修改路径

### 方案 A：安全修正优先（推荐）

保留“待办队列首页＋五类详情”的已确认结构，只修复队列归类、操作目标、上下文、核对结果、动作字段和命名。完成事项另分区，高风险动作必须显示精确目标与前后变化。

优点：直接降低误操作，改动集中，不引入新后台能力。缺点：仍是单账号、单队列的轻量原型，不能解决真实组织权限和工作分派。

### 方案 B：完整运营工作台

在 A 的基础上增加个人运营账号、事项归属、优先级、SLA、风险等级、交接、双人复核和更完整的审计。

优点：适合生产规模和高风险管理。缺点：明显扩大业务、权限和接口范围；当前没有足够确认，不能直接写入实施需求。

### 方案 C：只改文案和视觉

仅统一“运营处理/运营队列”“实收退款/实收与退款”等文字，并调整按钮颜色和卡片间距。

优点：成本最低。缺点：账号目标缺失、核对页不完整、完成事项混入待办等流程风险仍然存在。

**推荐 A。** B 只作为未来生产化决策清单，C 不足以满足本次发现的问题。

## 5. 推荐的信息结构

### 5.1 运营待办：首页分清“现在要做什么”

~~~text
┌────────────────────────────┐
│ ‹          运营待办      ··· ◎ │
├────────────────────────────┤
│ [全部类型⌄] [待处理⌄] [排序⌄] │
├────────────────────────────┤
│ 待你处理  7                 │
│ [举报] 洗衣机维修需求被举报    │
│ 待首次回应 · 目标剩余 3小时     │
│                              │
│ [费用核验] 维修佣金补充新材料   │
│ 待受理 · 2026/10/21 16:00     │
├────────────────────────────┤
│ 等待对方  1                 │
│ [待补充] ……                  │
├────────────────────────────┤
│ 最近完成                    │
│ [已出结论] 商家作品下架申诉     │
└────────────────────────────┘
~~~

- “待你处理”只能包含运营当前可执行且尚未完成的事项。
- “待补充”如果正在等待用户或外部材料，应进入“等待对方”，不能继续占用主动待办数量。
- “已出结论、已核对、已退回、验收通过”进入“最近完成”或历史记录。
- 排序规则必须明确。推荐优先级是“已超目标 → 临近目标 → 业务确认的高风险 → 提交时间”，但只有业务确认并有真实字段后才实施。
- 没有时限的费用、实收和故障事项只显示提交时间或风险信息，不伪造倒计时。

### 5.2 事项详情：先确认对象，再展示动作

~~~text
┌────────────────────────────┐
│ ‹          处置详情      ··· ◎ │
├────────────────────────────┤
│ 事项：R-101 · 举报           │
│ 内容对象：洗衣机维修需求       │
│ 当前状态：公开展示             │
│ 下一目标：首次回应             │
├────────────────────────────┤
│ 待核对事项 / 原处理上下文       │
│ 必要材料                    › │
├────────────────────────────┤
│ 本事项操作                  │
│ [请求补充] [确认无需处置]       │
│ [要求整改] [下架内容]           │
│                              │
│ 账号级操作                   │
│ 目标账号：<真实可核实账号>       │
│ [限制指定能力] [停用账号]        │
├────────────────────────────┤
│ 操作历史                    › │
└────────────────────────────┘
~~~

- 内容级和账号级操作分组，不把“下架内容、限制账号、封禁账号”当成同一层级的相邻按钮。
- 账号级操作未取得目标账号、当前限制和影响能力时保持不可执行，并说明缺少什么。
- “保存核对结论”按当前对象状态改成结果型名称：公开状态使用“确认无需处置”，已有处置使用“维持原处置”。
- 已出结论事项默认只读；如允许继续处理，必须先执行明确的“重新开启处理”或“新增后续处置”，并记录原因。

### 5.3 填写页：动作不同，字段名称也不同

当前通用字段“具体理由”不能覆盖所有任务。建议按动作显示：

| 动作 | 推荐字段 | 应保留的只读上下文 |
| --- | --- | --- |
| 记录首次回应 | 本次回应内容 | 事项摘要、首次回应目标 |
| 请求补充材料 | 需要补充的内容 | 已有材料、缺失项 |
| 要求整改 | 整改要求、整改截止 | 当前问题、影响对象 |
| 下架内容 | 下架依据 | 内容对象、当前公开状态 |
| 限制账号 | 目标账号、限制能力、期限、处置依据 | 当前账号状态、已有其它限制 |
| 停用账号 | 目标账号、恢复条件或是否永久、处置依据 | 账号影响范围、必要保留入口 |
| 维持原处置 | 核查依据 | 原结论、原理由、申诉新材料 |
| 费用核验 | 核准基数、核定余额、核验依据 | 原基数、锁定比例、封顶、原佣金、争议金额 |
| 实收分配 | 分配核对依据 | 支付引用、可分配金额、应缴项、暂缓项 |
| 恢复验收 | 验收引用、验收依据 | 故障标识、受影响交易、原有效到期 |

填写过程中不必重复所有详情，但不能让运营人员靠记忆完成金额、账号和故障范围的判断。可使用只读摘要和“查看必要材料”折叠区，返回详情时保留已填内容。

### 5.4 核对页：展示精确的“执行前 → 执行后”

~~~text
提交前核对

动作：核对实收并分配
事项：P-301

本次分配
PAY-A → BILL-A   ¥10.00
PAY-A → BILL-B    ¥5.00
PAY-B → BILL-B   ¥15.00

不会分配
BILL-C · 争议暂缓  ¥15.00

执行后
BILL-A 剩余 ¥0.00
BILL-B 剩余 ¥0.00
多收待退   ¥10.00

[返回修改] [确认分配实收]
~~~

各类核对页至少回答：

1. 操作对象是谁或是什么。
2. 当前值是什么。
3. 执行后会变成什么。
4. 哪些对象明确不受影响。
5. 如果失败或结果未知，下一步是什么。

具体要求：

- 费用核验显示原基数、原佣金、核准基数、重算佣金、差额和余额。
- 实收分配显示每条支付引用到每个账单的精确分配，以及暂缓项和多收金额。
- 解除处置显示“已下架 → 恢复展示”等真实目标状态。
- 账号限制显示目标账号、限制能力、期限及保留入口。
- 故障恢复显示验收引用、受影响交易和每笔新的保护截止。
- 最终按钮不再统一使用“确认记录”，而是“确认维持原处置”“确认下架内容”“确认限制账号 7 天”“确认分配实收”“确认记录恢复验收”。

## 6. 按优先级修改

### P0：操作对象和状态正确性

| 已观察问题 | 原则与影响 | 修改建议 | 验收标准 |
| --- | --- | --- | --- |
| “限制账号/封禁账号”核对页只有举报标题 R-101，没有目标账号 | 账号级处置不能由内容标题代替目标；运营无法确认影响谁 | 增加真实账号标识、当前账号状态、限制能力和影响范围；字段缺失时禁用账号级操作 | 核对页无需返回即可确认唯一账号、操作范围、期限和保留入口 |
| 费用、实收和故障核对页只有原则说明，没有精确结果 | “先核对再确认”只完成了形式，没有完成结果核对 | 使用第 5.4 节前后对照；所有金额、账单、交易和截止均来自同一版本快照 | 页面展示值与执行后日志完全一致；版本变化时阻止确认并重新计算 |
| 已出结论卡片仍位于“待你处理”下 | 标题承诺与列表内容不一致，待办数量和可见条目不匹配 | 分离待你处理、等待对方、最近完成/历史 | “待你处理 N 项”下只出现 N 个未完成主动任务 |
| 已出结论事项仍可直接“请求补充材料”并转回待补充 | 终态被隐式重开，用户和审计无法区分后续处理 | 业务确认重开规则；需要继续时使用“重新开启处理/新增后续处置”并记录原因 | 终态不能通过普通动作静默回到处理中；历史保留前后两段 |
| 共用管理账号无法识别实际操作者 | 对账号限制、退款和结论变更的责任链不足 | 原型可保留说明；进入生产前必须确认个人账号、代理身份或其它可审计机制 | 操作记录能定位授权主体；不得只依赖前端显示名 |

### P1：操作选择、字段语义和队列效率

| 已观察问题 | 修改建议 | 验收标准 |
| --- | --- | --- |
| 详情底部主操作直接取当前动作列表第一项；申诉和注销抵扣会优先显示“请求补充材料” | 按事项阶段配置“推荐下一步”，或只保留“选择处理操作”入口，不依赖数组顺序 | 主操作与待核对事项一致；无明确推荐时不替运营代选 |
| 所有动作复用“具体理由” | 使用第 5.3 节动作型字段名和提示 | 不查看影响说明也能知道应填写什么 |
| 整改、限制、封禁共用 1/3/7/30 天或永久 | 分别定义整改截止、能力限制期限和账号停用规则；在业务确认前不展示语义不通的选项 | 不出现“永久整改期限”；限制与封禁的差异可由文字独立解释 |
| “限制账号”和“封禁账号”边界不清 | 先确认实际能力范围，再按结果命名，例如“限制发布与接单 7 天”“停用账号” | 两个动作不会因名称相近导致同义或重叠 |
| 队列只有事项类型筛选，没有主动状态、等待状态或完成状态筛选 | 增加状态维度；有真实目标时再提供可解释排序 | 30 项队列能快速定位临近目标、待本人处理和等待外部事项 |
| 表单离开详情后不再显示原金额、原结论或故障范围 | 在填写页保留任务相关只读摘要和材料入口 | 金额、账号和故障操作无需靠记忆填写 |

### P2：命名、一致性和视觉扫描

- “运营处理”“A 运营队列”建议统一为“运营待办”；详情页仍按任务显示“处置详情、平台费用核验、实收与退款、故障保护”。
- “B 举报申诉”实际还包含内容巡查，建议改为“B 内容处置”，或在评审导航写“内容/举报/申诉”。
- “D 实收退款”和详情“实收与退款”统一为“实收与退款”。
- “保存核对结论”按状态使用“确认无需处置”或“维持原处置”；“操作已记录”回执按实际结果命名。
- 动作列表分成“事项处理”和“账号级操作”；危险动作不只靠红色，也靠分组、文字和最终确认表达。
- 队列卡片的“查看 ›”可以保留，但整卡可点击时不应让它看起来是唯一可点击的小目标。
- 详情内金额、期限和状态继续使用对齐布局；长说明优先放在展开区，关键差异不要埋在段落里。
- 保留当前 44px 左右触控高度、焦点样式、固定底栏、0.98 左右按压反馈和减少动态效果适配。

## 7. 推荐流程

### 7.1 举报、申诉和内容巡查

~~~text
运营待办
  → 进入具体事项
  → 核对对象、原结论和必要材料
  → 记录首次回应（如适用，不结案）
  → 选择事项级或账号级操作
      ↘ 账号级：目标账号和能力范围缺失则禁止继续
  → 填写动作型字段
  → 核对对象、前后状态、期限和不受影响项
  → 使用结果型按钮确认
  → 持久回执和操作历史
  → 最近完成
~~~

### 7.2 费用核验

~~~text
受理本次新增材料
  → 只暂停本次争议佣金
  → 原快照与新增材料并列
  → 填写核准基数和核定余额
  → 核对原值、目标值、重算佣金和差额
  → 确认保存核验结论
  → 有应补余额时生成补充通知
  → 以通知成功时间启动争议部分 72 小时
~~~

### 7.3 实收与退款

~~~text
核实支付引用
  → 预览精确分配
  → 排除争议暂缓项
  → 确认分配
  → 多收本金单列
  → 核对待退金额
  → 发起退回
      ↘ 结果未知：只查询，不重复发起
      ↘ 失败：保留可重试状态
      ↘ 成功：记录已退金额和核实时间
~~~

### 7.4 故障保护

~~~text
核对故障标识、证据和影响功能
  → 明确受影响交易
  → 记录已核实故障
  → 等待恢复验收
  → 核对验收引用和每笔目标保护截止
  → 确认记录恢复验收
  → 同事件重放不续期
~~~

## 8. 状态和动作规则建议

| 状态类型 | 队列归属 | 可见主操作 | 禁止误导 |
| --- | --- | --- | --- |
| 待处理/待受理/待核对/待记录 | 待你处理 | 与当前任务匹配的下一步 | 不按动作数组第一项自动替用户选择 |
| 等待对方补充 | 等待对方 | 查看补充要求 | 不继续计入主动待办 |
| 处理中/核验中/故障中 | 待你处理或处理中分区 | 查看最近进展、执行已确认下一步 | 不写成已有结论 |
| 操作结果未知 | 待你处理顶部 | 重新查询结果 | 不生成成功回执、不重复执行 |
| 已出结论/已核对/已退回/验收通过 | 最近完成或历史 | 查看结果 | 不继续混在待你处理 |
| 需要重新处理的终态 | 先确认重开规则 | 重新开启处理 | 不通过普通请求补充动作静默重开 |

## 10. 后续实施的验证方案

### 10.1 队列和状态

- 完成一个事项后，待你处理数量减少，完成卡片只进入最近完成，不再出现在待办分区。
- 等待外部补充的事项不计入主动待办；补充到达后再进入待你处理。
- 每种筛选和排序都能说明依据；没有目标的事项不显示虚假倒计时。
- 30 项以上队列可按类型、状态和已确认排序规则定位事项。
- 已出结论事项不能通过普通动作静默重开；合法重开保留旧结论和新处理段。

### 10.2 高风险操作

- 账号限制和停用显示唯一目标账号、具体受限能力、期限、恢复条件及不受影响入口。
- 内容下架、账号限制、停用、解除处置和退款最终按钮使用动作型名称。
- 费用核验的原值、目标值、重算结果、差额和执行日志一致。
- 实收分配预览与执行后每笔分配、多收和暂缓项完全一致。
- 故障恢复核对页逐笔显示目标保护截止，执行后不发生额外延长。
- 版本变化时核对页失效，保留输入并要求基于新版本重新核对。

### 10.3 布局、交互和无障碍

- 320、375、414px 无横向溢出，返回、单行标题和胶囊不碰撞。
- 长对象名、长理由、长操作历史、30 项队列和多笔分配可以滚动到底。
- 固定底栏不遮挡获得键盘焦点的字段、错误或动作。
- 错误摘要与字段错误一致，错误不只依赖红色，返回修改保留已填内容。
- 触控目标继续采用项目约 44px 尺度；按钮按压不造成布局跳动，减少动态效果下关闭缩放。
- 危险操作同时使用明确文字、分组、影响说明和最终确认，不只依赖颜色。

### 10.4 端到端联调

- V14 提交的事务编号在 V15 显示同一对象和安全摘要。
- V15 首次回应、请求补充和最终结论映射到 V14 对应记录，时间和状态不互相替代。
- 用户侧不可看到内部账号、内部理由或受限材料；运营侧也不能恢复已关闭凭据。
- 未知结果在两端均只对应一个事务，不因查询或刷新重复创建。
- 本地合成预览通过不等于生产接口、权限、通知、退款和故障日志已接入。
