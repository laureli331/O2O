# V15 二次优化实施记录

日期：2026-10-23。依据[审阅文稿](v15-ui-flow-naming-review-20261023.md)，用户要求实施二次优化。原文“只提供建议”是原评审阶段的边界，不代表本轮已确认其中所有业务决策。

## 已实施：不改变业务规则的核对修正

- 新增只读精确预览：在当前版本的副本上计算，不写入原事项、日志或支付事实；费用差额、实收逐笔分配和故障逐交易保护截止与实际合成执行使用同一计算。
- 填写页保留原结论、原金额、锁定标准、支付引用或故障范围等任务上下文；可查看原事项及必要材料，再返回继续填写，输入保留。
- 核对页显示对象、版本和精确前后变化；最终按钮带入动作，理由字段按当前任务命名。
- 故障恢复使用明确合成验收引用，不从证据说明中拼接或猜测引用。

参考：[GOV.UK核对信息](https://design-system.service.gov.uk/patterns/check-answers/)、[动作型按钮](https://design-system.service.gov.uk/components/button/)、[Atlassian队列说明](https://support.atlassian.com/jira-service-management-cloud/docs/check-out-your-queues/)。只借鉴核对、安全动作和可解释队列原则，保留本项目移动端视觉。

## 本轮实施

- 三段队列逐段显示数量并排序；等待补充、整改、补缴进入等待对方；已出结论、已核对、已退回、验收通过进入最近完成。结果待确认作为可恢复查询项保留。
- 内容操作与账号操作分区。账号目标来自合成事项明确关联，不根据标题猜测；限制必须勾选至少一项能力，封禁无期限选择器，解除必须选择一条具体限制。
- 事项与目标账号分别校验版本。同一账号的另一事项改变限制后，即使当前事项版本未变，原核对也失效；输入保留，必须重新核对。
- 终态普通写操作被模型拒绝；允许的内容事项只通过带理由的重开动作新增处理段。其它完成状态不借此变回处理中。
- 核对页明确显示原金额、目标金额、逐笔分配、争议不分配项、逐交易保护截止及继续生效的限制。精确结果也保留在操作日志，可展开回看，回执按动作结果命名。
- 详情主按钮使用明确首次回应、查询、重开或“选择处理操作”，不再取动作数组第一项。填写理由按任务命名，原上下文和返回后输入保留。

## V14—V15状态规则

这是已确认的概念映射，不是已存在的接口字段或本地联动实现：同一事项编号分别关联用户提交与运营处理；提交时间、首次回应时间、补充要求/补充提交、最终结论独立记录；结果未知保持同一事务，不重复创建。用户端只读有权看到的摘要、公开理由与进度，不暴露内部操作账号、内部理由或受限证据；运营仍不能恢复已关闭凭据。真实事务编号、权限、幂等与消息接入以后端核实为准。
