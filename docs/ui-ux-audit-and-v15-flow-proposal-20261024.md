## 先看结论

V15 当前的主要问题是任务被拆散：在详情看材料，换页填理由，再换页核对；选过的动作再次出现，下结论前又要返回材料。补齐材料解决了“没东西可看”，没有解决“怎样少费力地处理”。

### 页面使命与边界

用户：当前管理账号。进入：从待办队列选中一个具体事项。任务：核对原内容和材料，作出一次明确操作，知道是否成功。完成后：留在原事项显示结果，可返回原队列筛选与位置，或主动选择下一项。

本次合并展示与填写步骤，不合并业务事件：首次回应、请求补充、最终结论仍各自记录；不强制“先回应再结案”，也不自动伪造首次回应。不开启真实通知、处置、支付或退款。

方案A（推荐）：同页材料＋处理区，必要时一个确认弹窗。省去独立填写页、上下文中转页和整页核对，判断时能直接参照材料。

方案B：保留独立填写页，仅把核对页合入填写页。改动较小，但填写时仍需往返查材料，不能解决U02，因此不推荐作为本轮终点。

### 保留、删除、合并

| 处理 | 具体内容 |
| --- | --- |
| 保留 | 原内容及图片、举报/申诉原话、独立材料、处理动作、必要字段、实际理由、结果及日志。 |
| 删除 | 重复“你需要判断什么”说明卡；只重述原文的材料卡；独立填写页中的完整动作二次选择。 |
| 合并 | 详情＋填写；原文＋被举报位置；重要操作的影响核对合入一次弹窗。 |
| 弱化 | 编号、版本、完整历史；非当前操作的规则说明；低频账号动作收在“更多处理”。 |
| 不改 | 所属账号绑定、能力选项、1/3/7/30天、逐条解除、明确重开、资金分配和故障保护算法。 |

桌面示意：

```text
┌────────待办────────┬────────原内容与材料────────┬────本次处理─────┐
│ 类型/状态/搜索      │ 洗衣机无法启动，想上门检查 │ [选择处理方式 v] │
│ 当前选中事项        │ 图片 · 完整原文            │                 │
│ 其它待办            │ 被举报原句：……            │ 理由            │
│                    │ 举报人描述：……（待核实）   │ [补原图][补说明] │
│                    │ 新增材料（有才显示）       │ [可编辑输入框]   │
│                    │                            │                 │
│                    │ 更多信息与记录 ▾           │ [本次具体动作]   │
└────────────────────┴────────────────────────────┴─────────────────┘
```

窄屏为同一页面上下排列：原内容→举报/申诉及材料→本次处理。选择方式后只展开该动作的期限、金额、范围等字段；不再跳到另一个填写页。图片仍共享放大，关闭回到原位置。

### 提交与确认规则（关键决策待用户确认）

| 操作 | 建议交互 | 确认时必须看见什么 |
| --- | --- | --- |
| 记录首次回应、请求补充材料 | 在同页填写后直接记录 | 具体按钮说明动作；仍明确是否只是合成记录，不冒充消息已送达。 |
| 保存无需处置/维持原处置结论、明确重开 | 在同页填写后直接记录 | 操作旁说明会完成本段或重新开启；旧结论/首次回应/目标保持。 |
| 整改、下架、限制、封禁、解除 | 一次确认弹窗 | 对象、影响、选中能力/限制条目、期限/截止和理由；无关字段不显示。 |
| 费用核定、通知生成、实收分配、退款相关操作 | 一次确认弹窗 | 与该动作直接有关的精确金额、分配、原截止/新截止及资金状态；不能只留下模糊摘要。 |
| 故障保护记录、恢复验收 | 一次确认弹窗 | 日志/验收引用、影响交易及逐交易保护截止；未知与成功分开。 |

重要操作默认焦点在“返回修改”，取消后保留填写和材料滚动位置。常规操作点击前已有同页明确摘要，不自动执行其它业务事件。未得到本表确认前，不删除现行独立核对流程。

### 理由短句

1. 按当前动作显示3～5个相关短句；不默认选中，不打开页面就自动填理由。
2. 点击只插入文本，可继续编辑；已有文字不被覆盖，重复点击同一短句不重复堆叠。提供撤销最近一次插入，保留用户原有文字。
3. 仍执行现有1—1000字校验，超长时说明剩余空间，不截断用户输入。
4. 切换动作更新短句，不自动把旧理由改成新的结论；已输入内容保留，由用户核对是否适用。
5. 账号处罚、金额核定等不能用“已核实违规”等空泛通用句替代具体依据。用提示帮助补全对象、材料和原因，不自动编造事实。
6. 不新增AI调用、常用语后台管理或真实跨账号同步。

可审阅的短句示例：

| 动作 | 可点击短句示例 | 点选后的处理 |
| --- | --- | --- |
| 记录首次回应 | “已收到，正在核对原内容与相关材料。” | 填入回应框，仍需用户点击记录。 |
| 请求补充 | “请补充被举报内容的原图。”／“请说明具体有问题的句子或图片。”／“请补充与本事项对应的凭据。” | 可组合并编辑，不自动发送。 |
| 整改 | “请修改被指出的描述，使其与实际服务范围一致。” | 仍需明确当前对象与整改期限。 |
| 无需处置 | “所举报的问题未出现在当前原文中。” | 仅用户核对后手动选择；不根据点击自动选结论。 |
| 下架 | “原文包含与本条需求无关的服务推广内容。” | 仅适用于用户已核对的对应内容；不是系统判断。 |
| 费用/实收/故障 | 根据当前动作提示核对材料、金额或验收引用 | 不能凭短句制造已付款、已退款、验收通过等事实。 |

### 必须闭环的状态

| 状态 | 必须出现的行为 |
| --- | --- |
| 未选操作/理由缺失 | 就近指出缺什么，保留材料与已有填写，不创建记录。 |
| 材料缺失 | 明确缺原文或材料，不显示邻近事项的内容；保留回应/补充路径。 |
| 成功 | 原事项更新结果、时间与当前状态，按钮按新状态变化；不另开空白成功页。 |
| 失败 | 留在处理区，保留所有填写，可重试。 |
| 结果未知 | 显示“查询这次结果”，阻止重新提交；刷新后仍可恢复查询。 |
| 版本变化 | 保留理由，读取最新材料后重新核对动作和范围，不覆盖新状态。 |
| 取消确认 | 回到原处理区，理由、范围、金额和位置保留。 |
| 离开未提交内容 | 依既有草稿/离开规则处理，不静默清空；不因新增短句绕开现有规则。 |

## 6. 后续页面设计的统一检查表（提案）

每个页面先写清用户、进入条件、主要任务、首先要看的信息、主要操作、成功/失败/取消、完成去向和禁止重复项。不能说明能帮助用户作什么决定的模块，不直接加入界面。

验收时依次检查：无需额外解释能否理解任务；能否找到内容与操作；能否预测后果；能否完成并知道结果。长句、重复标题、空泛介绍、无事可做的入口逐项检查。必要的风险和权限不能以简洁为由删除。

本表尚未写入AGENTS.md；先用V15检验，不能把未经用户确认的交互分类推广成项目硬规则。

## 7. 外部参考与本项目建议的区别

- [Reddit审核队列](https://support.reddithelp.com/hc/en-us/articles/15484440494356-Moderation-Queue)：原文、举报理由和上下文可以连在一起阅读。用于材料与处理同页的研究依据，不照搬处罚/批量操作。
- [GOV.UK Check answers](https://design-system.service.gov.uk/patterns/check-answers/)：支持提交前核对并回去修改。它并未证明V15所有动作都必须独立一整页，也没有替本项目决定哪些操作可省确认。
- [Zendesk手动应用常用回复](https://support.zendesk.com/hc/en-us/articles/4408887656602-Using-macros-to-update-tickets)：可手动应用预设文本并在提交前编辑。本项目只借鉴文字插入，不附带自动改状态、分派或发送操作。

上述是官方公开文档查证，不是已经实际体验这些平台最新内部后台的证据。第5节的布局、确认分类和短句细则均为本项目待确认方案。
