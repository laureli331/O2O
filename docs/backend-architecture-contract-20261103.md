## 1. 验证方案与权威来源

本轮先检查现有规范和实际探针，再按当前PRD逐项核对模块归属、依赖方向、状态与事务、幂等唯一性、权限、错误、追踪及恢复。文档/JSON须一致，任务引用真实存在、依赖无环、原状态不改变；运行现有计划和全量测试，另外对新增合同执行只读覆盖与负例检查后提交Git。上述检查不等于正式后端验收。

依据依次为：当前会话用户强约束与AGENTS.md、[最新shared方案](unified-react18-shared-core-20261030.md)、[主PRD](prd.md)及最新明确确认、[原验收合同](v1-quality-acceptance-20261027.md)。[参考对话](chatgpt-conversation://6ae9c65e-beb0-83e8-9f7f-fcefef617152)仅提供审查方法；其示例目录、订单状态及模型名称不覆盖本项目决定。

本轮采用codebase-design的Module/Interface/Implementation/Adapter原则：Module以少量、明确的Interface封装完整职责；Interface同时说明前置、不变量、顺序、错误、配置和验证要求，不限于TypeScript类型。仅在确有平台/供应商/测试替身差异时使用Adapter，不增加无实际用途的BaseService、GenericManager或通用交易引擎。

## 2. 架构形态与依赖方向

保持一个逻辑业务后端和一份共享业务核心，以模块化单体方式组织。云函数可有多个入口，这不意味着引入独立微服务、独立业务库或另一套规则。本文的17个职责模块不是17个npm包、17个云函数或要求提前建立的空目录，随SP功能按需形成。

```text
Web / Taro展示层
  -> shared/react、shared/state、application/client公开入口
  -> shared/api请求编排 -> 注入的平台传输Adapter

云函数入口：传输解析、取得可信身份、构造本请求依赖、调用用例
  -> shared/application中服务器可用的用例入口
  -> shared/domain的唯一规则与shared/contracts的契约
  -> 经接口注入的CloudBase数据库/时钟/存储/供应商Adapter
```

| 层/位置 | 职责 | 禁止依赖/行为 |
| --- | --- | --- |
| shared/contracts | 全部自有DTO、事件、结果、错误类别与能力接口；定义未知输入的合同 | 不导入UI、平台SDK、客户端状态或用例实现，不复制第二份业务类型 |
| shared/domain | 分模块纯规则、金额/时间/版本不变量和状态转换；不直接访问I/O | 不导入application、api、state、react、平台Adapter或云SDK |
| shared/application | 客户端及服务器用例分别提供明确入口；组织规则、授权、事务、模块协作 | 服务器入口不导入React、浏览器/微信对象、客户端api/state；客户端用例不反向导入state，通过结果或接口交互 |
| shared/api | 统一业务请求封装、版本、幂等键、错误与未知结果查询 | 底层HTTP/云调用由注入Adapter完成，不在端侧复制，不直接使用fetch/wx |
| shared/state、shared/react | 会话内状态/actions、双端相同业务Hooks和view-model | 不引入另一套规则；store按会话创建，云端不导入、不共享用户实例 |
| shared/ports | 如需单独入口，仅重导出contracts中的能力Interface | 不定义重复契约，不装入平台实现 |
| platform-adapters | 传输、可信身份、数据库事务、文件、时钟、供应商协议等I/O实现 | 不做计价、计佣、交易资格、状态迁移或权限业务判断，不反向让shared导入自身 |
| apps端侧展示 | 展示、布局、读取原始输入、平台生命周期桥接及绑定shared动作 | 不计算佣金/费用，不自行判断业务资格、推进交易状态、复制请求流程或定义自有Interface |
| 云入口/composition | 白名单路由、注入可信依赖、调用shared服务器用例、编码响应 | 不因信任客户端结果跳过服务端校验；不在入口复制另一套业务流程 |

服务器用例仍属于shared。所谓“服务器可用”必须由导出清单和实际依赖图证明不携带React、客户端store或平台API；不能把I/O编排挪到云入口后就宣称应用流程已经共享。

每个业务Module对外提供只读事实或命令Interface，调用者不能直接修改其内部记录。跨Module的原子流程由shared/application协调，给各Module传同一事务上下文；Domain之间不为读取状态而循环依赖。需要的事实通过contracts传入，不再独立推导他人规则。

## 4. 命令Interface、授权与未知结果

以下是必须承载的逻辑合同，不是已经存在的HTTP路由、SDK签名、数据库表名或错误码。

1. 外部输入为unknown，校验类型、字段白名单、长度、枚举、金额和当前版本后收窄。客户端提供的角色、资格、佣金、当前时间、所有权和已付款均不作为可信事实。
2. 命令包含明确对象、操作、客户端操作键、载荷及必要的期望版本；可信actor、应用/经营归属、服务端时钟和当前数据由服务器取得。Webhook另按实际通道核验来源，不能套用客户端登录或截图。
3. 幂等范围至少区分可信actor/归属、操作和操作键。同键同载荷返回原处理状态/结果；同键不同载荷拒绝。不同真实支付不是同回调；新一次明确操作不暗用旧键。
4. 幂等记录的接受、业务写入、必要版本与可靠事件意图必须在可证明的一致性边界内。不能先“查不存在”再分别写，也不能业务已成功但仅因结果响应失败就新建一次动作。
5. 操作结果分成功、明确拒绝/失败、处理中、结果未知；未知使用原请求的有权查询，不自动重发副作用。网络/供应商超时不等于业务失败，更不能返回成功。
6. 业务拒绝、版本冲突、身份/权限不足、输入非法、基础设施/供应商失败分开。具体编码和SDK错误映射由SP08/SP13据实际文档确定；对外保留安全错误类别和请求标识，内部追踪，不回传密钥/原证件/私密正文。

Web与微信最终使用同一用例和权限规则，但可信身份取得路径各自验证。尚未确定的Web登录/托管实际能力按原SP02/SP04/E02/E06补证，不以客户端自报管理账号代替。

## 5. 状态机与跨Module事务边界

状态不能用一个“成功”字段合并。至少独立表达需求/申请、正式交易、费用/延期/取消/交付异议、故障保护、佣金、付款/抵付/退款、广告权益、评价数值/图文/回应。物理枚举以当前PRD与SP08合同为准，不新增“手动完成/收到确认”。

| 事务场景 | 必须一致的读写事实 | 失败/竞争与验证要求 |
| --- | --- | --- |
| TX01 接受任一副作用命令 | 当前权限/对象版本、幂等接受记录、操作结果及同次业务变更 | 同键异载荷拒绝；请求成功后断网、重复请求和不同actor同键不能重复或串单 |
| TX02 正式选人/闲置确认 | 当前有效申请/时间/费用告知、需求当前轮次唯一承接、交易、原佣金标准快照、必要联系授权、事件意图 | 两人并发只能一成功；闲置必须买家确认当前版本；任何失败不留下部分授权/快照或另一交易 |
| TX03 费用/内容/延期确认 | 当前版本双方明确同意、原/新有效快照；关联内容与费用须都满足才一起生效 | 待确认不覆盖旧值；新内容不能被旧同意带过；拒绝/撤回保留历史，不因请求自动改到期 |
| TX04 正常结束与异议/保护 | 当前有效到期、有效交付异议/解除版本、故障及恢复保护、唯一结束事实、权限回收及事件意图 | 截止有效收到的异议及时，严格超过且无阻断才结束；取消不复活。SP08须证明可信接收时点、持久化顺序和竞争优先级，不能自行加宽限或用客户端时间 |
| TX05 形成主计佣 | 合法正常结束及有效费用/首次补费窗口、原标准快照、唯一主记录、实际形成月份和事件 | 未知费用不填0、不能因结束就立即造佣金；7.4补费窗口/费用异议独立。已有主记录更正不再新造主记录或二次封顶 |
| TX06 实收与抵付/多收 | 已验证渠道付款唯一事实、当前可缴项、按最早到期的分配、剩余应缴和多收待退 | 争议暂缓款不自动占款，部分缴纳不刷新期限；不同实际付款都留事实，同回调只一次；退款不令原有效抵付重新欠缴 |
| TX07 退款申请与确认 | 原付款、实际可退/已退/处理中金额、唯一退款操作、渠道请求及可核对结果 | 并发不能超退；渠道未知先查，不重复发起；0拟退不造转账；入驻/制作/广告位/多收各依本来的规则 |
| TX08 领券与核销 | 当前活动/有效期/经营资格、账号限领、库存与本人券；核销核对当前码/版本、所属商家及一次结果 | 最后一张不超发；换码旧确认失效；核销最多一次；停领/入驻到期不能作废已领有效券 |
| TX09 广告区间占用/释放 | 已通过素材、完整区间、固定位置、主体重叠限制、实际保留期限及付款/核对状态 | 单次预查询“无重叠”不是并发安全证据；SP08/SP27须用经验证的冲突锚点/串行化或等价原子机制验证相邻与重叠区间；未知不释放重售 |
| TX10 评价与修改/回应 | 当前资格/方向/自然人、窗口、唯一数值与一次修改消耗、当前图文/回应版本和可见汇总版本 | 重试不多耗机会，旧审核不覆盖新候选；数值与内容审核独立；列表与汇总版本一致，不靠永久混版容忍错误 |
| TX11 审核通知与入驻窗口 | 审核当前版、站内消息实际成功生成事实及对应72小时窗口起点 | 待发意图不等于站内消息已成功生成；不等已读或微信送达。只审核通过或写入发送队列不能提前启动窗口 |
| TX12 实际成功出账 | 当前应缴来源、账户/月份唯一账单及项目一致版本、成功出账时点与期限 | 计划时间/队列开始不是成功出账；失败/部分批次不能公开成完整账单或启动72小时。实际事务规模和分批发布协议须SP08验证 |

事务重试可能多次执行回调，不在事务回调里调用支付/退款、AI、发送通知或其他外部副作用。外部调用使用已持久化的唯一意图/操作，渠道幂等/查询能力据真实文档验证；不能宣称所有外部系统能够exactly-once。

提交业务事实后才发消息不够可靠：SP08/SP11必须证明业务提交与持久发送意图的原子关系，以及失败领取、重放、去重和恢复。优先验证同库事务中的发送意图；如复用平台原生可靠投递，须提供等价保证和故障测试。不因此默认采购或引入消息中间件。

## 6. 数据库与唯一性/迁移合同

不把文档数据库当SQL数据库，不假定其有外键、范围排他约束或特定索引能力。SP08须给物理对象/字段/索引、事务读写集、查询入口、访问所有者和实际SDK映射，查证当前版本限制，再以真实受控并发验证。逻辑键可用唯一索引或确定性标识加事务等经验证方法实现，不能只靠应用层if。

| 必须保障的不变量 | 逻辑唯一性/关联范围 |
