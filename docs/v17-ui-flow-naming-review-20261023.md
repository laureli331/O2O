# V17「历史维修经历」UI、流程与命名复核稿

日期：2026-10-23  
性质：修改建议稿，仅供评审；本轮不修改 `v17.html`、脚本、样式或业务规则。

## 1. 结论先行

V17 的“只看合法历史、不恢复新发起”边界已经守住，列表、详情、空态和未登录态也都能成立。当前最需要修正的不是页面结构，而是两组概念没有彻底拆开：

1. **记录处理状态**：这条历史经历最后如何结束；
2. **评价资格状态**：这条记录现在能否进入 V18 评价。

目前只有存在“首次资格时间”的详情才显示评价状态；未达成一致、等待结束、已撤回等记录没有明确写出“不可评价”的原因。与此同时，这些记录底部仍出现主按钮“查看评价记录”，容易让用户误以为当前记录已经有关联评价。

建议把 V17 定位为“历史记录查询页”，每条详情都明确给出处理结果和评价资格；只有真正可评价的记录才显示主操作“去评价”。

## 2. 已核对范围与验证方式

本稿基于以下实际检查，不根据页面名称推测功能：

- 正常列表：7 类合成历史记录；
- 可评价详情：`H-1`，可进入 `v18.html?source=H-1`；
- 不可评价详情：未形成一致确认、等待期结束、已撤回、等待处理、暂无法核实等；
- 空态：“暂无历史经历”；
- 未登录态：“登录后查看本人历史”；
- 375px 视口下的列表、详情、长内容滚动、底部操作和横向溢出；
- 现有模型测试所覆盖的 320px、375px、414px 三档窄屏。

已确认且不在本稿中改动的业务边界：

- V17 只展示既有、合法的历史记录；
- 不提供新建、重新确认、撤回、重提等写入入口；
- 当前订单仍从服务页进入；
- 只有通过既有资格校验的记录才能进入 V18 评价。

## 3. 外部参考与本项目适配

| 已查证的公开做法 | 解决的问题 | 本项目如何适配 | 不照搬的内容 |
|---|---|---|---|
| [Atlassian Design System：Lozenge](https://atlassian.design/components/lozenge) 将标签用于简短、易扫读的状态，并区分进行中、成功、警告、错误等语义 | 让用户快速判断当前状态 | 保留卡片右上角的短状态，但只表达“记录处理状态”；评价资格另起一行说明 | 不复制其颜色值、状态集合或桌面端密度 |
| [GOV.UK Design System：Button](https://design-system.service.gov.uk/components/button/) 区分主操作与次操作，避免同一区域出现多个同等突出的选择 | 降低错误点击和行动歧义 | 详情底部只让“去评价”在满足资格时成为主操作；通用导航降为次级 | 不复制政府网站的视觉样式 |

以上是公开设计规范，不代表已实际体验这些平台的最新应用界面。下面的方案是结合本项目小程序场景、既有页面风格和已确认规则形成的建议。

## 4. 问题与修改建议

### P1-01：不可评价记录缺少明确的资格结论

**现状**

详情仅在记录带有 `eligibleAt` 时显示“首次资格时间”和“评价状态”。因此，`H-2` 等记录只看到“处理结果”，看不到“为何不能评价”的明确结论。

**风险**

用户需要自行从“未形成一致确认”等处理文案推断评价资格；“处理结束”和“可以评价”容易被理解为同一件事。

**建议**

每一条历史详情都固定展示两个独立字段：

| 字段 | 示例 | 展示规则 |
|---|---|---|
| 处理状态 | 双方已确认 / 未形成一致确认 / 已撤回 | 所有记录必显 |
| 评价资格 | 可评价至 10月30日 / 未形成评价资格 / 已过评价期 / 等待结果 | 所有记录必显 |

“首次资格时间”属于辅助信息，只有资格曾经成立时再显示，不承担资格结论的职责。

### P1-02：非关联操作被表现成当前记录的主操作

**现状**

不可评价详情的底部为“返回历史 / 查看评价记录”，后者使用主按钮样式并跳到 V18 通用页面。

**风险**

“查看评价记录”在当前详情语境中像是“查看这条经历的评价”，但实际只是进入通用评价管理页。

**建议**

- 可评价：`返回历史` + 主按钮 `去评价`；
- 不可评价：只保留主路径 `返回历史`；如确需跨页入口，在详情正文末尾提供弱链接 `查看我的评价`；
- 不使用“查看评价记录”，除非未来能够保证它打开当前记录对应的评价详情。

### P2-01：卡片分类和标题重复

**现状**

卡片同时出现标签“维修经历”和标题“历史维修经历 · 台灯检修”。

**建议**

标题只保留具体对象或事项，例如“台灯检修”；“维修经历”由标签承担，“历史”由页面标题和所在列表承担。

### P2-02：状态词同时混用过程、结果和资格

建议采用两层词表，避免自由发挥：

| 当前/可能出现的表达 | 建议放置位置 | 建议统一为 |
|---|---|---|
| 已确认 | 记录处理状态 | 双方已确认 |
| 未达成 / 无一致 | 记录处理状态 | 未形成一致确认 |
| 超时 / 等待结束 | 记录处理状态 | 等待期已结束 |
| 已撤回 | 记录处理状态 | 已撤回 |
| 等待中 | 记录处理状态 | 等待处理 |
| 无法核实 | 记录处理状态 | 暂无法核实 |
| 可以评价 | 评价资格 | 可评价至 {日期} |
| 已评价 | 评价资格 | 已完成评价 |
| 过期 | 评价资格 | 已过评价期 |
| 不符合 | 评价资格 | 未形成评价资格 |

其中“等待期已结束”是否必然对应“未形成评价资格”，仍以现有模型规则为准；UI 只展示模型返回的最终结论，不自行推导。

## 5. 建议布局

```text
┌────────────────────────────┐
│ ‹  历史经历详情       ··· ◎ │
├────────────────────────────┤
│ 维修 · 历史记录             │
│ 台灯检修                     │
│ 对方        王**             │
│ 记录时间    2026-10-20       │
├────────────────────────────┤
│ 处理结果                     │
│ 双方已确认                   │
│ 已完成必要核查……             │
├────────────────────────────┤
│ 评价资格                     │
│ 可评价至 2026-10-30          │
│ 首次资格时间 2026-10-23      │
├────────────────────────────┤
│ 查看记录来源                 │
├────────────────────────────┤
│ 返回历史          [去评价]   │
└────────────────────────────┘
```

不可评价时，第三块仍然保留，但内容改为明确原因；底部不再出现与当前记录没有直接关系的主按钮。

## 6. 建议流程

```text
历史列表
  └─ 选择一条记录
       └─ 历史详情
            ├─ 处理状态：始终显示
            ├─ 评价资格：始终显示
            ├─ 可评价 → 去评价 → V18 对应评价表单
            └─ 不可评价 → 返回历史
```

页面不新增任何记录写入分支，也不在 V17 重新计算资格。

## 8. 实施后的验收清单

- 7 类历史详情都同时显示处理状态和评价资格；
- 只有资格允许时出现“去评价”，并携带正确记录编号；
- 不可评价详情不再以主按钮暗示当前记录存在评价；
- 列表与详情使用同一套状态词，不出现同义词漂移；
- 空态、未登录态不出现写入操作；
- 320px、375px、414px 下无横向滚动，长原因可完整换行；
- 底部按钮不被小程序安全区遮挡，按下有轻微缩放或明暗反馈；
- 键盘焦点、返回路径和读屏名称可用；
- 原有模型、页面和全量回归测试全部通过。
