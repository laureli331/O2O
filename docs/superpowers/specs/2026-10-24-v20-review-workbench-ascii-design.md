# V20 评价审核工作台 ASCII 优化设计

日期：2026-10-24  
状态：页面结构已经用户确认，主 ASCII 与本地合成 HTML 已落实；真实审核、通知及身份权限后端未接入。
修改目标：优化 `docs/ascii-design-prd-2.1.md` 中 V20-A～C，使运营审核逻辑完整、页面职责清晰且没有重复页面。

## 0. 本轮界面优先级（覆盖下文原表格展示方案）

V20任务式界面优化确认（2026-10-24）：用户确认按“看评价、做判断”的顺序重做界面。默认仅显示待我处理，等待补充、已处理与全部可切换；卡片展示首图、标题、评价摘要、待办动作与时限。详情先评价、后处理，编号、版本、检测和日志折叠；普通评价只选“允许公开/不予公开”，服务经历核实与申诉保留独立动作。原审核模型、证据、版本、数值资格与未知结果保护不变，仍为本地合成预览。

默认待办卡片，先前表格及编号、版本优先的展示方式不再采用；四类任务路由与全部业务保护继续有效。初次提交直接展示评价，修改评价才并列展示旧版和本次修改。长标题最多两行，完整标题在详情可读。预览身份、场景与模拟结果折叠在外层“预览设置”，不占日常工作区。

参考 [GOV.UK Task list](https://design-system.service.gov.uk/components/task-list/) 的任务名称与状态表达，以及 [Check answers](https://design-system.service.gov.uk/patterns/check-answers/) 的提交前核对。它们支持任务清晰和核对原则；卡片首图、评价优先和两工作台分工为本项目适配，不代表外部平台原样界面。

验证：六项呈现测试覆盖默认筛选、搜索、排序、动作、影响说明及空内容；浏览器覆盖四类流程与失败/未知恢复、折叠信息、长内容、五种宽度及44px操作目标。

## 1. 已确认决策

用户已确认以下方案：

1. V20 跟随 V15/V16，采用“网页主后台＋小程序轻量值班入口”。
2. 采用方案 A：一个统一队列、两个职责互斥的审核工作台，共保留 V20-A、V20-B、V20-C 三个页面合同。
3. 不按任务类型或处理状态复制列表页、详情页、历史页或结果页。
4. 图文/回应进入 V20-B；目录经历资格核查/评价申诉进入 V20-C。
5. 小程序只承载提醒、数量和只读摘要；审核结论、版本操作、资格变更在网页后台完成。

## 2. 外部公开参考

本设计查阅的是公开设计规范和产品帮助，不把它们写成已经实机体验相关平台最新内部后台的证据。

| 公开参考 | 已查证做法 | V20 适配 |
|---|---|---|
| [Atlassian Dynamic Table](https://atlassian.design/components/dynamic-table/) | 动态表格集中提供分页、排序等列表能力 | 一个队列承载四类评价任务，类型和状态作为筛选条件 |
| [IBM Carbon Data Table](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines) | 表格工具栏承载筛选等全局动作；行操作属于当前对象 | 筛选不生成新页面；点击行进入当前案件工作台 |
| [Atlassian Panel](https://atlassian.design/components/panel/usage) | 详情面板适合筛选、设置或上下文详情，并保持一致触发方式 | 网页端可采用队列＋详情工作台；ASCII 仍按独立页面合同表达，不限定具体前端框架 |

不照搬外部平台的处罚体系、处理时限、自动化能力、角色权限或申诉次数；V20 只使用本项目已经确认的规则。

## 3. 页面信息架构

```text
网页主后台
└─ V20-A 统一处理队列
   ├─ 图文审核任务 ───────────────→ V20-B
   ├─ 回应审核任务 ───────────────→ V20-B
   ├─ 目录经历资格核查 ───────────→ V20-C
   └─ 评价申诉 ───────────────────→ V20-C

小程序轻量入口
└─ 待处理数量 / 逾期提醒 / 只读案件摘要
   └─ 提示到网页后台继续处理
```

V20-A～C 是三个不同页面合同：

- A 负责寻找和选择任务；
- B 负责对当前图文版本或一次回应作审核结论；
- C 负责基于必要证据核查资格，或复核已有评价结论。

## 4. V20-A 统一处理队列

### 4.1 页面职责

在一个列表中查看所有评价相关运营任务，通过筛选快速定位，不直接执行高风险结论。

### 4.2 页面内容

- 页面标题：`评价审核`；
- 待处理、已逾期、待补充三个摘要数值；
- 类型筛选：全部、图文审核、回应审核、目录经历核查、评价申诉；
- 状态筛选：待处理、待补充、处理中、已逾期、已结论；
- 搜索：案件编号或评价编号；
- 列表字段：案件编号、类型、关联对象摘要、当前状态、提交时间、24小时目标、版本；
- 默认顺序：提交时间从旧到新；逾期使用明确状态标记，但不改变已经确认的业务时限；
- 点击整行进入 B 或 C，队列本身不展示通过、拒绝、开放资格等结论按钮；
- 加载失败保留最近成功列表并标记过期，提供重试；空态区分“当前筛选无任务”和“当前没有任务”。

### 4.3 不生成的重复页面

- 不为四种任务建立四个列表页；
- 不为待处理、逾期、驳回、申诉中建立状态页；
- 不建立单独搜索结果页；
- 不建立单独已完成队列页，“已结论”只是筛选状态。

## 5. V20-B 内容与回应审核工作台

### 5.1 页面职责

审核一个明确的当前候选版本。图文与回应复用同一页面骨架，但根据任务类型展示不同材料和结论说明。

### 5.2 固定结构

1. **案件头部**：案件编号、任务类型、状态、提交时间、24小时目标、当前版本；
2. **评价上下文**：业务、评价方向、资格来源、打码作者与被评对象；
3. **独立事实**：数值评分是否有效、当前合法公开图文/回应、当前候选版本；
4. **候选材料**：图文任务展示文字＋全部图片；回应任务只展示1—300字文字，不出现图片入口；
5. **检测结果**：通过、命中、失败、未知分别展示；检测结果不是人工结论；
6. **公开影响**：初稿未通过则不公开；修改待审或拒绝继续展示旧合法图文；合法数值不因图文拒绝失效；
7. **处理历史**：版本提交、检测、人工结论、理由、通知结果和时间线；
8. **结论区**：通过或拒绝，运营理由1—1000字必填；提交前显示对象、版本和公开影响摘要。

### 5.3 版本与结果保护

- 只允许处理当前候选版本；
- 提交前重新校验任务仍属于当前版本；
- 旧版本迟到结果不能覆盖当前候选版本；
- 重复请求不能重复公开、通知或改变评分；
- 失败时保留理由和选择；
- 结果未知时只允许查询本次请求，不提供盲目重提；
- 只有服务端确认成功才显示已通过或已拒绝。

### 5.4 不生成的重复页面

- 图文和回应不各建一套详情页；
- 当前公开版、候选版和历史版不各建页面；
- 版本历史在本工作台内折叠展示；
- 图片查看使用共享预览层；
- 提交核对使用共享确认层；
- 成功、失败、未知使用同页结果区域，不建立结果页。

## 6. V20-C 资格核查与评价申诉工作台

### 6.1 页面职责

处理依赖必要证据的资格核查，或复核已有评价相关结论。两类任务共用案件、证据和时间线骨架，但结论动作互不混用。

### 6.2 固定结构

1. **案件头部**：案件编号、类型、状态、提交时间、首次回应目标；
2. **来源与角色**：业务来源、双方角色、自然人/来源去重结论、历史记录；
3. **当前事实**：当前评价资格、数值状态、公开内容/回应状态、原处理结论；
4. **必要证据**：只向必要管理权限展示，不向公众或另一方扩散原稿、身份或私密材料；
5. **处理进展**：待首次回应、待补充、处理中、已有结论分别显示；
6. **完整时间线**：提交、首次回应、补充请求、材料到达、结论、通知；
7. **动作区**：记录首次回应、请求必要材料、填写有依据的结论。

### 6.3 按任务类型显示结论

目录经历资格核查：

- `确认实际完成并开放评价资格`；
- `现有依据无法认定，不开放评价资格`。

评价申诉：

- `维持原结论`；
- `有依据更正原结论`，并明确新的结论及影响对象。

所有结论都须记录实际理由、前后状态、管理账号和时间。共用账号日志不能声称识别具体自然人操作者。

### 6.4 边界

- 24小时首次回应不等于24小时结案或全天值守；
- 无法认定时不开放评价资格；
- 资格核查不恢复联系方式，不造交易、计佣、付款或争议解除事实；
- 合法低分、相同IP/住址、双方分数不同、付费客户身份都不能单独证明评价虚假；
- 只有基于实际依据确认无资格或虚假记录时，才能让数值评分失效并从统计排除；
- 内容违规结论不能自动替代数值资格结论；
- 申诉是引用原结论的新复核阶段，不覆盖或删除原处理记录。

### 6.5 不生成的重复页面

- 资格核查和评价申诉不各建一套详情骨架；
- 首次回应、请求补充材料、证据历史和结论历史不各建页面；
- 原处理结论以内嵌摘要＋时间线展示；
- 申诉不会复制 V20-B 原审核页。

## 7. 状态流

### 7.1 图文或回应审核

```text
提交当前候选版本
  → 检测中
     ├─ 检测失败/未知 → 保持未公开并标异常 → 人工继续核对
     └─ 取得检测结果 → 人工待审
                           ├─ 通过 → 公开当前合法版本 → 通知
                           ├─ 拒绝 → 不公开当前版本 → 通知原因
                           └─ 超过24小时 → 标逾期，仍不自动通过
```

### 7.2 资格核查或评价申诉

```text
案件提交
  → 待首次回应
     → 已首次回应
        ├─ 材料不足 → 待补充 → 材料到达 → 处理中
        └─ 材料足够 → 处理中
                         └─ 有依据的结论 → 通知并保留历史
```

首次回应、处理状态和最终结论是三个独立事实，不能用一个“已处理”状态替代。

## 8. 网页与小程序分工

| 能力 | 网页主后台 | 小程序轻量入口 |
|---|---|---|
| 待办数量、逾期提醒 | 完整 | 展示 |
| 列表筛选、搜索、排序 | 完整 | 不提供 |
| 必要只读摘要 | 完整 | 展示 |
| 原稿、图片、私密证据 | 必要权限查看 | 不展示 |
| 审核通过/拒绝 | 执行 | 不执行 |
| 开放/否定资格 | 执行 | 不执行 |
| 更正申诉结论 | 执行 | 不执行 |
| 版本历史、并发校验、结果查询 | 完整 | 只显示状态与网页提示 |

CloudBase 数据控制台不作为日常运营界面；两端以后端同一权限、状态、版本和日志为准。

## 9. ASCII 改写范围

此节记录此前ASCII阶段范围。用户随后明确要求“开始制作”，本轮据此实现网页主后台与小程序只读HTML，并确认申诉仅更正原案件的同一个图文版本、回应或评价资格，不扩展账号处罚。实现、参考适配和验证见[HTML预览说明](../../v20-html-preview.md)。

后续只修改下列内容：

- `docs/ascii-design-prd-2.1.md` 的 V20-A、V20-B、V20-C；
- V20 页面组说明和必要的验收映射文案；
- 与新结构直接相关的测试。

不改动 V18/V19 用户评价规则、V14 用户举报申诉入口、V15 通用运营处置、评分算法、审核时限、数据保留期限或真实接口状态。

## 10. 验证方案

### 10.1 页面去重

- V20-A、V20-B、V20-C 各出现一次；
- 队列、工作台和小程序入口职责互斥；
- 状态、历史、确认层、预览层没有被画成重复子页面；
- 图文/回应只进入 B，资格/申诉只进入 C。

### 10.2 业务闭环

- 四类任务都有明确入口、材料、动作、结果和返回路径；
- 图文、回应、资格、申诉的状态流无断点；
- 24小时审核结果和24小时首次回应不混用；
- 合法数值、图文版本、回应版本和资格状态保持独立；
- 失败、未知、逾期、版本冲突和待补充均有恢复路径。

### 10.3 边界与权限

- 小程序不能执行高风险审核或资格变更；
- 私密证据不进入公开页或轻量入口；
- 低分、付费、相同IP/住址、双方分数不同不能单独触发失效；
- 不新增删差评、自动通过、恢复联系、确认付款或代判服务争议能力。

### 10.4 文档与自动检查

- ASCII 每个方框等宽闭合；
- 页面覆盖矩阵与 V20-A～C 一致；
- Markdown 围栏、表格和本地链接有效；
- 新增 V20 专项文档测试；
- 运行 `node --test tests/ascii-design.test.cjs`；
- 运行项目全量 `node --test`；
- 修改后只提交本任务文件，不包含工作区既有无关改动。
