# 第一版发现页与底部导航调整设计

日期：2026-10-18
状态：用户已批准，等待用户审阅书面规格后再制定实施计划

## 1. 目标

第一版底部导航调整为“首页 / 发现 / 发布 / 服务 / 我的”。取消“消息”作为底部一级页面，将必要通知入口迁到“服务”页右上角。第一版新增面向商家主帖的“发现”页和基础发布、审核流程。

本次实施对象仅为仓库中的规划文档、设计交接资源、自动化合同测试与 HTML 交互预览。当前仓库没有小程序业务源码；本次不创建或修改小程序源码，也不启用真实发布、审核、通知、支付或商业化。

## 2. 已确认的产品边界

### 2.1 底部导航

- 顺序固定为：首页、发现、发布、服务、我的。
- “发布”继续位于中央，并延续当前强调样式。
- “服务”由第二位移到第四位，原服务目录和管理能力不删除。
- 删除底栏“消息”入口及其一级页面定位，但不删除业务所需的站内通知记录。
- “服务”页右上角提供通知入口；存在未读通知时显示未读角标，无未读时不显示角标。

### 2.2 发现页内容范围

- 第一版发现页只展示审核通过且当前允许展示的商家主帖。
- 居民发布的维修、跑腿、闲置和其它需求继续由首页承载，不进入发现信息流。
- 第一版允许审核通过的商家自行提交主帖。
- 第一版基础发帖不绑定工具会员、内容加热或付费资格；第二版商业化方案继续延后，不因本次调整自动启用。
- 第一版不提供评论、点赞、关注、热榜、付费加热或个性化推荐。
- 支持查看主帖详情、收藏和微信分享。

## 3. 信息架构与入口

### 3.1 首页

首页继续承载居民交易与需求信息，不混入商家主帖瀑布流。本次只更新底部导航，不改变既有首页业务分类和流程。

### 3.2 发现

发现页采用图片优先的双列瀑布流，参考小红书的浏览节奏和信息密度，但不复制小红书的品牌色、品牌图标、素材或专属文案。界面继续使用本项目既有的绿色、米白和低饱和视觉体系。

信息流默认按审核通过后的发布时间倒序展示。第一版不使用热度、互动量或个性化算法排序，避免产生刷量、冷启动和排序解释问题。

### 3.3 发布

中央“发布”入口继续提供维修、跑腿、闲置、其它四类居民发布。只有已通过商家审核的账号额外看到“商家主帖”入口；普通居民不显示该入口，尚未通过审核的商家只能看到申请或状态指引，不能提交主帖。

### 3.4 服务与通知

“服务”保留维修、跑腿公开服务资料和现有服务管理能力。页面右上角增加通知入口，集中承载选人、费用确认、异议、到期、审核结果及其它必要业务通知。

通知中心是“服务”的二级页面，不是底部一级页面，也不是自由聊天工具。通知正文不得包含完整电话、详细地址、证件信息、领取码或未审核附件。

### 3.5 我的

“我的”继续承载本人资料、交易、收藏、草稿、地址簿、账单、帮助和资格状态。本次不把通知入口重复放到“我的”。

## 4. 发现页交互设计

### 4.1 信息流卡片

- 使用双列瀑布流，封面图片优先展示。
- 标题最多显示两行，超出部分视觉截断，不改写原文。
- 卡片底部显示商家头像、商家名称和审核标识。
- 不展示未经核实的销量、成交量、评分或虚构互动数。
- 点击卡片进入商家主帖详情。

### 4.2 主帖详情

- 支持查看 1 至 9 张图片，按商家确认的顺序展示。
- 展示完整标题、正文、商家身份、服务区域和发布时间。
- 提供收藏、取消收藏和微信分享。
- 通过商家资料入口查看其已获授权公开的信息。
- 不提供评论、点赞、关注或私信。

### 4.3 状态与反馈

- 首次加载显示与卡片结构一致的骨架屏。
- 无内容时说明当前暂无已审核商家内容，并提供返回首页服务的入口；不得用虚假帖子填充。
- 加载失败时保留当前已成功加载内容，并提供明确的重试按钮。
- 收藏、取消收藏和重试操作提供即时反馈；失败时恢复到操作前状态并说明未成功。
- 按钮按下时轻微缩小，松开后恢复；收藏成功使用短暂、克制的状态变化。
- 系统开启“减少动画”时取消非必要缩放和过渡，不影响状态辨识。

## 5. 商家主帖合同

### 5.1 内容字段

- 图片必填，至少 1 张、最多 9 张；第一张默认作为封面。
- 发布前可调整图片顺序并更换封面。
- 第一版只支持图文，不支持视频。
- 标题必填，最多 20 个可见字符。
- 正文必填，最多 1,000 个可见字符。
- 不增加与标题、正文重复的“宣传短句”等字段。

可见字符的具体统一计数实现由后续实施计划引用项目现有 Unicode 计数规则，不按 UTF-16 代码单元错误拆分表情或扩展字符。

### 5.2 商家身份与公开信息

- 主帖自动关联已审核的商家档案和服务区域，商家不能在帖子中选择或冒用其他经营档案。
- 帖子表单不单独填写手机号、微信号或详细地址。
- 用户只能在商家资料页看到商家已经明确授权公开的电话和地址。
- 商家档案变更按既有资格规则重新审核；审核期间不自动改写已发布主帖。
- 本设计不创造新的商家审核材料、行业准入接口或核验能力；这些内容继续以项目已有规则和真实核验结果为准。

## 6. 发布与审核流程

状态流为：草稿 → 预览确认 → 提交审核 → 待审核 → 已发布，或待审核 → 审核未通过。

- 草稿允许不完整，仅本人可见，不进入发现页。
- 提交前必须预览并由商家明确确认，不自动发布。
- 审核未通过时必须向商家显示可理解的原因，允许修改后重新提交。
- 修改已发布主帖时，线上旧版继续展示，新版本单独进入审核。
- 新版本审核通过后原子替换旧版；审核未通过时旧版保持不变。
- 发现违法、侵权或明显风险时，运营可立即下架当前公开版本并保留操作记录；不得以“新版审核中”为由阻止必要处置。
- 审核结果通过“服务”右上角通知入口告知商家。

## 7. 兼容现有规划

- 第一版商家基础发帖免费开放给审核通过的商家，不继承第二版工具会员的付费门槛。
- 第二版工具会员、内容加热、广告、推广池、价格、退款和统计方案仍保持延后状态；本设计不授权真实收费或推广。
- 现有“发现页商家主帖主信息流”的第二版推广范围描述可以保留，但实施文档必须明确区分：基础发现与基础发帖进入第一版，付费加热仍属第二版候选能力。
- 现有站内消息为主、有条件微信通知的规则继续有效；只是入口层级调整，不把通知失败解释为业务失败，也不删除必要记录。

## 8. 无障碍、隐私与安全

- 底栏、通知按钮、收藏、分享和重试入口需有明确可访问名称和键盘焦点样式。
- 交互目标应满足当前项目移动端点击区域标准；图标不能成为唯一状态表达。
- 商家审核、主帖审核、下架及通知访问均需由服务端权限校验；HTML 原型只演示状态，不代表真实鉴权已完成。
- 公开卡片、搜索、分享和通知不得夹带私密地址、未授权联系方式、证件或未审核原图。
- 合成演示内容必须继续明确标注为演示，不得写成真实商家、真实审核结果或真实交易。

## 9. 实施范围

后续实施计划应精确列出受影响文件，至少覆盖：

- 当前 PRD、结构化设计、开发计划、ASCII 页面规格、UI 交接说明和项目上下文。
- V01 至 V05 HTML 预览中复用底部导航的页面。
- 新的发现页、主帖详情、商家主帖发布与审核状态 HTML 预览，或在现有预览体系中等价覆盖这些状态。
- 对应 Node 合同测试、预览验证脚本和必要的 PowerShell 静态检查。

不得改动当前工作区中与本设计无关的 `redbook` 删除记录，不得把它们纳入本次提交。

## 10. 验证与验收

### 10.1 自动化合同

- 所有底栏实例的标签和顺序均为“首页 / 发现 / 发布 / 服务 / 我的”。
- 底栏不存在“消息”入口；“服务”页右上角存在通知入口和可验证的未读状态。
- 发现信息流只接受当前已审核、可展示的商家主帖，拒绝居民交易信息和未审核版本。
- 普通居民、待审核商家和已审核商家的发布入口权限分别符合本设计。
- 图文类型、1–9 张图片、20 字标题和 1,000 字正文边界均有正反例。
- 已发布内容修改时，旧版与待审核新版分离；只有审核通过才替换公开版本。
- 私密字段不得出现在卡片、详情、分享或通知合同中。

### 10.2 交互与视觉

- 在 320、375、414 像素视口检查瀑布流、底栏、服务页通知入口、发布表单和详情页，无横向溢出或遮挡。
- 检查加载、空、失败重试、未登录、无商家资格、待审核、审核不通过、已发布和风险下架状态。
- 验证按钮按压、收藏反馈及减少动画设置。
- 验证现有首页、居民四类发布、服务和“我的”主要路径仍可使用。
- 浏览器运行无未处理异常或控制台错误。

### 10.3 回归与提交

- 运行仓库现有全量 Node 测试及相关 PowerShell 验证脚本。
- 人工核对 PRD、结构化设计、开发计划、页面规格、预览和测试之间没有版本范围冲突。
- 实施改动使用独立 Git commit；只暂存本次相关文件，以便完整回滚。

## 11. 非目标

- 不修改或创建小程序业务源码。
- 不接入真实商家、真实内容、真实审核、真实通知或真实微信分享。
- 不实现视频、评论、点赞、关注、热榜、推荐算法、内容加热、会员收费、广告或支付。
- 不补造商家准入接口、审核时限、存储期限、供应商能力或运营人力承诺。
