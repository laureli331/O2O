## 每次测量的记录字段

每个设备/网络/页面/角色/状态组合单独记录，不混合不同构建、设备、网络或工具条件：

- 唯一运行编号、责任 SP 卡、质量条款及测试组；开始/结束时间和轮次/片段编号。
- 精确构建身份：Git 提交、锁文件/依赖版本、构建模式、运行配置及数据集/内容边界。
- 设备型号、系统、微信版本、基础库、页面渲染器、实测刷新率、字体/视口设置；Web 端记录 Windows、浏览器版本、视口和缩放。
- 页面/角色/状态、操作步骤、网络类型/注入参数、缓存条件、数据集规模和内容特征。
- 测量工具名称、版本或提交、二进制/脚本哈希（若可得）、计时源、时间分辨率、采样开销和采集配置。
- 原始样本及不可变证据路径；合同阈值来源；逐组逐轮统计、预期与实际结果。
- 失败/超时/未知结果、复现输入、修复提交、同条件复验和受影响组回归结果；结论及复核人。

缺少原始样本或关键条件时，不得只保留聚合百分位并判通过。工具无法观察目标渲染层或不能对齐用户输入时，应标为方法能力不足；不能把宿主窗口统计或系统总内存冒充产品层测量。

## 原门槛的引用方式

具体阈值以 [质量验收合同](v1-quality-acceptance-20261027.md) 及其 JSON 为唯一来源，本登记不复制或覆盖它们。记录中按实际适用情况关联 QP05（真实 60Hz、每组 3 轮、每轮至少 30 段持续操作片段、每段平均至少 55 FPS、无超过 100ms 的应用可归因卡顿/视觉跳变/错触）、QP06（逐端点拆分并由实际证据形成和确认预算）、QP08（用户确认的 60 分钟/至少 60 个完整循环/每 10 分钟记录，内存预算和可观察方法仍按原门槛确认）及 QP09（实际 Web 页面、任务、浏览器和已确认预算）。不适用的组须记录理由和责任卡，不得将“尚无页面”写成通过。

QP10 仍要求每组、每轮分别达标；参数/原始证据缺失或任一适用组失败即不通过。所有失败保留并按原条件复测，最终候选全量复验归 SP35。

## 复用调查与测量方法边界

- **项目内复用：**复用现有 QP10 合同、SP07/后续责任卡和 `node:test`；登记使用 JSON/Markdown，不新造测量 SDK 或运行时接口。
- **微信官方能力：**现有 [微信小程序 `wx.getPerformance`](https://developers.weixin.qq.com/miniprogram/dev/api/base/performance/wx.getPerformance.html) 与 [PerformanceEntry](https://developers.weixin.qq.com/miniprogram/dev/api/base/performance/PerformanceEntry.html) 类型用于性能阶段项；项目核对过的微信维护型 [API typings](https://github.com/wechat-miniprogram/api-typings) 未声明 FPS/逐帧指标。因此它们可用于记录启动/渲染阶段项，不作为 QP05 帧率测量替代。
- **系统级方法：**SP01 已核对 Android [Perfetto FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline) 的本地样例。样例能观测微信 AppBrand 宿主层，但没有证明独立小程序 WebView 的呈现帧或应用卡顿归因；不能直接作为产品 FPS 通过证据。后续方法必须在对应真实页面和条件下证明可归因性。
- **依赖/许可/维护：**本入口没有引入或复制第三方代码，也没有增加依赖；因此没有新的许可证、升级或供应链负担。今后若需采用新测量依赖，应在对应 SP 卡按 AGENTS.md 单独核对源码、许可、维护、兼容和回退，并做最小验证。
- **适配与验证：**只新增证据登记文档，并由仓库现有 Node `node:test` 断言登记字段、责任卡和未测状态；不连接云端、不修改 QuickStart、不采集真实用户数据。
