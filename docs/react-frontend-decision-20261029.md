2026-10-30用户强约束覆盖旧版本建议：两端React/DOM/相关类型统一18.3.1，TS统一5.9.3，全部业务集中shared，UI分开，禁止平台API进入shared及自有any。最新[架构与配置计划](unified-react18-shared-core-20261030.md)、[精确版本策略](frontend-version-policy-20261030.json)。React19实验只作历史，不是现行候选。

日期：2026-10-29。用户已确认小程序与网页后台都使用React，并回复“通过”确认Taro方案。配套[结构化记录](react-frontend-decision-20261029.json)。本记录覆盖旧原生小程序方向，保留原批准记录作为历史。精确版本与真实构建仍须核验；下文提案过程中的“待确认Taro”已由本段覆盖，不再重复询问。

## 已确认范围

用户提出“我希望用react”，在澄清“仅后台”与“小程序和后台都用React”的两项选择后回复“2”。因此，当前小程序前端方向改为React＋TypeScript；网页后台也采用React＋TypeScript。此前Vue建议未被采用。Node.js云函数、CloudBase、业务规则、价格、既定页面/视觉和权限验收标准继续沿用。

这里确认的是框架方向，不代表已批准Taro或某个精确版本，更不代表已经建立SP07工程。原生小程序探针所得平台环境、身份、事务和存储证据保留；框架编译、页面生命周期和性能须在新组合下重新验证，不能直接继承。

## 建议的具体方案（待用户确认）

| 层 | 建议 | 边界与代价 |
| --- | --- | --- |
| 微信小程序 | Taro＋React＋TypeScript，编译到微信目标后由微信开发者工具调试 | 增加编译/运行适配层；微信组件、API和生命周期仍需适配，不是浏览器React原样运行 |
| 网页运营后台 | React＋TypeScript＋Vite | 独立Web组件与浏览器构建；不通过小程序H5产物强行承担电脑后台 |
| 共同部分 | 同一服务端、可共享的纯类型/规则/请求契约 | 不承诺两端UI组件、样式、路由或登录逻辑直接通用；服务端仍执行最终权限、金额、时间和状态规则 |

[Taro官方仓库](https://github.com/NervJS/taro)明确支持React开发微信小程序。本轮npm只读查得CLI与React适配包4.3.1，CLI要求Node≥18，而@tarojs/react的React peer为^18。故建议先以React18.3.1作为兼容候选，不能直接拿此前后台查询的React19.3.1套入Taro。两端可先验证同一React18主版本，是否最终一致以各自完整构建和运行结果为准。

Taro的Vite runner4.3.1声明vite^4，与此前Web候选Vite8.3.5不是同一兼容范围。两端构建工具不强求共用版本；小程序编译器（Webpack/Vite）及TypeScript版本需核对模板与插件组合后决定。此前TS7＋微信类型的原生小片段检查不能证明Taro/React支持TS7。

不推荐把浏览器React页面直接塞进web-view来满足本次要求：这会另行引入网页承载及微信能力桥接，不能假定它等价于当前已确认的小程序页面合同。也不自行编写新的React小程序渲染器。本项目建议复用已有适配方案Taro，但其采用必须先确认。

## 实施顺序与验证方案

1. 先记录双端React已确认，Taro适配层/完整版本组合待确认；不再次询问是否采用React。
2. 适配层确认后，在独立隔离目录核对精确依赖、peer约束和锁文件；验证Taro微信目标真实构建产物、开发者工具编译与CloudBase调用入口，后台独立验证构建。不改QuickStart、不将探针当正式产品。
3. 隔离验证覆盖一个最小页面的状态更新、输入保留、按钮反馈、页面返回和错误恢复；明确合成环境与真机差异，出现兼容问题先复现再修复。框架性能开销按既定设备/测量计划验证，不预先承诺更快。
4. SP01—SP06的原交付、必要确认和质量合同门槛继续执行；SP07满足依赖后才建立正式目录与产品测试。源码维护React/TSX，不手改生成产物作为长期修复。
5. 最终逐页视觉、胶囊/安全区、键盘、长内容、大字、交互和真实权限仍按原合同验收；不得因换框架减少功能或降低门槛。

本地记录按本轮Git提交可回退；回退记录不自动撤销用户已确认的React意愿。若适配层验证失败，应记录失败并提交替代方案，不能擅自退回原生方向或改用Vue。验收状态不因本文升级。
