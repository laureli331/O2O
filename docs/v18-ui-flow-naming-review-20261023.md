# V18「评价与回应」UI、流程与命名复核稿

日期：2026-10-23  
性质：修改建议稿，仅供评审；本轮不修改 `v18.html`、脚本、样式或业务规则。

## 1. 结论先行

V18 已具备待评价、我评价的、收到的、评分、一次修改、提交结果查询和回应等主流程，且三项星级没有默认值，这些基础方向正确。

当前首要问题是“待评价”列表中的最终资格没有成为唯一状态来源：已经评价的记录会同时出现“这次经历已经评价”“可评价”和“暂不可评”。这是逻辑冲突，不只是文案问题。其次，页面首屏会把焦点移到标题，浏览器可能显示突兀的黑色焦点框；表单错误汇总虽可聚焦，但还不能直接跳到对应的评分组。

建议先统一状态来源，再调整页面命名、焦点和错误定位，不扩张现有业务功能。

## 2. 已核对范围与验证方式

实际检查包括：

- “待评价”正常、已评价、异议处理中、已取消、已过期等记录；
- 从 `S-NEW` 进入首次评价表单；
- 三项评分均未选择时提交，检查顶部错误汇总、焦点和字段提示；
- “我评价的”列表、详情、剩余修改次数、修改期限和版本记录入口；
- “收到的”列表、详情、回应表单及回应公开说明；
- 图文待审、图文未通过、检测待核实、审核超时、回应未通过、回应已公开、修改超期、资格失效、空态和未登录态；
- 375px 视口下的滚动、底部操作和横向溢出；现有测试覆盖 320px、375px、414px。

已确认且不在本稿中改变的规则：三项 1—5 星均必选且无默认值；文字、图片可选；数值评分与图文审核分开；首次有效提交后只有一次自主修改；回应只属于被评对象，公开后不可自行修改；提交结果未知时先查询，不能重复提交。

## 4. 问题与修改建议

### P0-01：同一卡片同时给出互相冲突的资格状态

**实际表现**

已经评价的 `S-OLD` 同时显示：

- 顶部：“这次经历已经评价”；
- 左下：“可评价”；
- 右下：“暂不可评”。

原因是顶部和禁用状态取自最终资格判断，左下仍取原始来源状态。

**建议**

所有可见状态与按钮都只读取最终资格结果，不再直接使用原始来源状态拼文案。

| 最终状态 | 左下说明 | 右下动作/状态 |
|---|---|---|
| 可评价 | 截止 {日期} | 去评价 › |
| 已评价 | 已于 {日期} 完成 | 已评价 |
| 异议处理中 | 结果确认后再判断 | 暂不可评 |
| 已取消 | 未形成评价资格 | 暂不可评 |
| 已过期 | 评价期限已结束 | 已过期 |
| 资格失效 | 经核查不再纳入 | 资格已失效 |

更彻底的做法是让“待评价”只显示仍可行动或等待结论的记录，把“已评价”移出该列表；见 D18-1。

### P1-01：“评价管理”偏后台口吻

这是本人侧页面，且三个页签都是个人评价记录。建议统一为：

- 页面标题、跨页导航：`我的评价`；
- 产品能力说明：`评价与回应` 可继续作为外部文档或模块描述；
- 页签继续使用：`待评价 / 我评价的 / 收到的`。

这样能减少“我是在管理全站评价还是自己的评价”的疑问。

### P1-02：首屏程序化聚焦导致标题出现突兀描边

当前首次渲染也会把焦点放到页面标题；在部分浏览器中，用户未进行键盘操作便会看到黑色矩形焦点框。

建议：

- 首次打开列表不强制移动焦点；
- 从列表进入表单、详情或提交结果等“页面级切换”时，仍将焦点移到新标题，保证读屏用户获知上下文变化；
- 为程序化标题焦点设计与页面一致的样式，同时保留键盘可见焦点，不能简单使用 `outline: none`。

### P1-03：错误汇总不能精确定位到三组评分

当前顶部汇总只有一段“请为态度、效率、沟通各选择1—5星”，字段处也有提示，这是好的基础。但用户仍需自行寻找三个未完成区域。

建议把错误汇总改为三条链接：

```text
请核对后再提交
• 请选择态度评分
• 请选择效率评分
• 请选择沟通评分
```

点击后聚焦对应评分组的第一颗星；选完该组后移除其字段错误。不要在用户仍未完成其它组时自动提交。

### P2-01：演示场景名称没有表达“评分已生效、图文另审核”

外层演示工具中的“修改图文待审”“修改图文未通过”容易让评审者误以为整个修改都未生效，但场景内数值评分已经更新。

建议改名：

| 当前 | 建议 |
|---|---|
| 修改图文待审 | 修改已提交，图文待审 |
| 修改图文未通过 | 评分已生效，图文未通过 |

这只调整演示命名，不改变真实业务规则。

### P2-02：禁用卡片仍像可点击入口

不可评价项使用整卡按钮但被禁用，视觉上仍保留“详情 ›”式信息架构。建议二选一：

- 若不提供详情：使用普通信息卡，不显示箭头；
- 若需要解释原因：卡片仍可进入只读详情，具体评价按钮单独禁用。

不要让“不可评价”和“不可查看原因”被同一个 `disabled` 同时决定。

## 6. 建议流程

```text
我的评价
  ├─ 待评价
  │    ├─ 可评价 → 首次评价表单 → 提交
  │    │                         ├─ 成功 → 结果页 → 详情
  │    │                         ├─ 失败 → 留在表单并说明原因
  │    │                         └─ 未知 → 查询结果，禁止重复提交
  │    └─ 不可评价 → 展示唯一、明确的最终原因
  ├─ 我评价的 → 详情 → 符合规则时修改一次
  └─ 收到的 → 详情 → 符合规则时回应一次
```

## 7. 待确认的关键决策

1. **D18-1（推荐）**：“待评价”只保留可评价和等待结论的记录；已经评价、已取消、已过期的记录不再长期占据该列表。若业务需要保留，则必须使用上表中的单一状态表达。
2. **D18-2（推荐）**：本人侧页面统一命名为“我的评价”，不再使用偏后台语气的“评价管理”。
3. **D18-3（推荐）**：首次打开列表不自动聚焦标题；页面级切换继续聚焦标题并设计可见焦点样式。
4. **D18-4（推荐）**：错误汇总拆成可定位的三条评分错误链接。

未确认前，本稿不改变页面行为。

## 8. 实施后的验收清单

- 任一卡片同一时刻只出现一个最终资格结论；
- 已评价项绝不再出现“可评价”或“暂不可评”；
- 三组星级初始均未选中，鼠标、触屏、键盘和读屏均可操作；
- 错误汇总获得焦点，每条错误可定位到对应评分组；
- 首屏无无缘由的标题黑框，键盘导航仍有清晰焦点；
- 提交成功、失败、未知三种结果不产生重复评价或重复消耗修改次数；
- 图文待审/未通过时，已生效评分与此前公开图文的关系说明一致；
- 320px、375px、414px 下无横向滚动，底部操作不遮挡，按钮有轻微按压反馈；
- 原有模型、页面和全量回归测试全部通过。
