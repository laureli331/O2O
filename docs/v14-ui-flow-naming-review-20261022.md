# V14 通知、举报申诉、处理记录与提醒设置修改建议

日期：2026-10-22（Asia/Shanghai）

实施追记：用户随后要求依本文二次优化，并确认D1/D2采用推荐任务型结构、D4采用两个独立开关。D3仅本地合成恢复查询，D5仍待E03，D6仅显式合成原记录字段；真实接口和办理能力不在本轮启用。下文保留原评审时点的建议与待确认状态，实施以[实施记录](v14-ui-flow-implementation-20261022.md)为准。

文稿状态：本稿是对 V14 合成交互预览的新一版独立评审，只提供修改建议，不修改现有 HTML、CSS、JavaScript，也不启用真实举报、申诉、图片上传、微信通知或个人信息处理能力。下文标为“建议”或“待确认”的内容均不是已经生效的业务规则。

审阅对象：[V14 通知与帮助预览](http://127.0.0.1:8765/v14.html)。本次覆盖 V14-A—E 五组页面，并对照现有 PRD F12、V14 ASCII 方案和 V14 预览说明；不评审 V15、V16 运营后台，也不重新定义 E03 尚未确认的个人信息字段、期限和授权文本。

## 结论

V14 已经建立了比较可靠的底层框架：未登录隔离、只看本人记录、失效对象安全投影、错误摘要、草稿、提交结果待核实、固定底部操作、44px 触控高度和减少动态效果都值得保留。当前主要问题不是视觉风格，而是五类任务被放进了两个含义过宽的复合入口，导致标题、首页顺序和操作文案不能准确回答“我现在处理的是什么”。

建议采用“**通知负责告知，处理记录负责跟进，申诉从原记录发起，个人信息权益独立说明，提醒设置单独管理**”的任务型结构。优先解决以下 5 项：

1. 申诉表单补回既有 ASCII 方案要求的原处理对象、处理理由、结论时间，避免用户脱离上下文申诉。
2. “提交结果待核实”必须在离开当前页后仍有可找回入口，不能返回处理记录后凭空消失。
3. 个人信息页在 E03 未确认时，不再写成已经存在“人工办理”能力；必须明确当前是否可申请、从哪里申请。
4. 处理记录首页先显示记录和待办，再显示帮助与设置；“我的接单资料”移回接单资料或账号设置。
5. 修正窄屏复合标题、提醒设置错误文案、危险操作主次和小号灰字对比度。

本文给出推荐方案和待确认项，不授权实施。任何真实申诉资格、状态节点、个人信息申请入口、提醒粒度和后台查询能力，仍须以可核实业务与接口事实为准。

### 1.2 已验证为正常、建议保留

- 30 条通知执行“全部已读”后仍保留 30 条记录，未读数归零，按钮禁用。
- 失效通知不会恢复旧地址、联系方式或附件，只显示安全摘要。
- 举报校验失败后，错误摘要获得焦点，并可跳到相应字段；已填内容不被清空。
- 文字草稿和本地图片边界分开：草稿可保存文字，图片不跨页、不伪装上传成功。
- 提交结果未知时阻止重复提交，要求先查询；成功、失败、待核实没有混成同一状态。
- 记录时间线区分提交、首次回应和最终结论，明确“24 小时首次回应”不等于 24 小时结案。
- 固定底栏、返回按钮、单选行、开关和折叠项具备足够触控区域；按钮有轻微按压反馈，并适配减少动态效果。
- 浏览器控制台未发现页面脚本错误或警告。

### 1.3 本次不假定

- 不假定任何举报或申诉都具备申诉资格、固定次数、固定结案时限或自动恢复权限。
- 不假定“提交结果待核实”已经有真实服务端查询接口、幂等键或持久记录。
- 不假定“到期提醒”和“催回复提醒”一定应共用一个开关。
- 不假定个人信息访问、更正、删除已经有在线表单、客服渠道、身份材料或处理期限。
- 不新增撤回、催办、客服联系、站外通知、自动退款或自动删除等未确认能力。
- 不把公开平台的做法当成本项目已接入或已体验其最新版产品的证据。

## 3. 三种信息架构方案

### 方案 A：任务型双中心（推荐）

“通知中心”只负责告知变化和深链；“处理记录”负责待补充、处理中、待确认和已有结论。申诉只能从符合条件的原记录进入；个人信息权益放在规则与隐私区域；提醒设置从通知中心或设置进入。

优点：每个入口只有一个主要目的；与现有权限和状态模型一致；不必新增底部导航。缺点：需要重排 V14-C、V14-D，不能继续依赖两个复合标题承载全部功能。

### 方案 B：四个完全独立页面

拆成“通知中心 / 处理记录 / 帮助中心 / 提醒设置”，申诉和个人信息权益分别作为处理记录与帮助中心的子页。

优点：层级最清楚，后续扩展容易。缺点：第一版入口较多，可能增加跳转和开发量；当前帮助内容不足以支撑一个独立“帮助中心”。

### 方案 C：保留当前复合页面，只做排序和改名

保留“申诉与个人信息事项”“我的处理记录与帮助”，仅缩短标题、把记录前置并修正文案。

优点：改动最小。缺点：入口仍混合两类或三类任务；随着内容增加会再次变得难以命名，320px 标题问题只能缓解，不能解决根因。

**推荐 A。** 它既保留 V14 当前页面数量和既有深链，又把核心任务边界说清楚，不需要为了完整感创造未确认的客服、数据请求或申诉能力。

## 4. 推荐页面结构

### 4.1 通知中心：告知变化，不承载处理后台

```text
┌────────────────────────────┐
│ ‹          通知中心      ··· ◎ │
├────────────────────────────┤
│ [全部] [未读 2]   全部标为已读 │
├────────────────────────────┤
│ • 举报事项需要补充说明         │
│   洗衣机维修需求 · 请补充事实    │
│   今天 09:20                 │
├────────────────────────────┤
│   跑腿订单有新的进展           │
│   帮忙代取一个快递 · 当前约定    │
│   今天 09:45                 │
└────────────────────────────┘
```

- 标题优先写“什么事项发生什么变化”，减少“你提交的事项有新进展”这类泛化通知。
- 摘要不得出现私密地址、完整电话、证件或附件内容；失效事项继续使用安全投影。
- 点击通知直接进入当前仍有权查看的订单或处理记录；全部已读只改变读状态，不改变业务状态。
- “全部已读”如保留当前短文案，需在 Toast 或辅助说明中明确“不删除记录”；空间允许时可用“全部标为已读”。

### 4.2 处理记录：首页先回答“我还要做什么”

```text
┌────────────────────────────┐
│ ‹          处理记录      ··· ◎ │
├────────────────────────────┤
│ 待你处理                    │
│ [待确认] 举报是否提交成功      │
│ [重新查询提交结果]             │
│ [待你补充] 洗衣机维修需求       │
├────────────────────────────┤
│ 全部记录                    │
│ [处理中] ……                  │
│ [已出结论] ……                │
├────────────────────────────┤
│ 帮助与设置                   │
│ 规则与隐私说明               › │
│ 提醒设置                    › │
│ 个人信息权益                › │
└────────────────────────────┘
```

- 将“我的处理记录与帮助”缩短为“处理记录”，避免 320px 两行标题。
- “待你处理”只放用户可执行事项；普通处理中和已有结论放入全部记录。
- “常用帮助”移到记录之后，并改为“帮助与设置”；“我的接单资料”移回 V10 对应的接单资料或账号设置入口。
- 待确认提交必须能在此恢复查询；若真实后端没有可持久查询能力，页面不得假装已经支持。

### 4.3 申诉：从原结论进入，表单保留上下文

```text
┌────────────────────────────┐
│ ‹          提交申诉      ··· ◎ │
├────────────────────────────┤
│ 原处理摘要                   │
│ 对象：本人内容处理事项         │
│ 结论：维持原处理              │
│ 理由：<真实可展示理由>          │
│ 作出时间：2026-10-21 09:00    │
│ [查看完整处理记录]             │
├────────────────────────────┤
│ 请补充与本次结论有关的新事实     │
│ [1—1000 字文本框]             │
│ 相关图片 · 选填，最多 9 张      │
├────────────────────────────┤
│ [保存文字草稿]      [提交申诉]  │
└────────────────────────────┘
```

现有 V14 ASCII 已明确申诉页应显示“原处理对象/理由/时间”，但当前可见表单只显示“本人内容处理事项”和通用说明。这不是新增业务，而是补回既有方案，属于流程正确性修复。理由只能展示真实记录中允许本人查看的内容，不能由前端拼接或推测。

### 4.4 个人信息权益：先诚实说明能力状态

```text
┌────────────────────────────┐
│ ‹        个人信息权益    ··· ◎ │
├────────────────────────────┤
│ 你可以了解                  │
│ 访问、更正、删除等事项需要核对  │
│ 身份、处理目的和依法保留范围。   │
├────────────────────────────┤
│ 当前办理方式                 │
│ [未确认时：在线申请暂未开放]     │
│ [确认后：显示唯一真实办理入口]   │
├────────────────────────────┤
│ 规则与隐私说明               › │
│ 查看相关处理记录             › │
└────────────────────────────┘
```

当前页面写“人工办理”，但没有办理入口、联系渠道或可执行下一步，用户会把说明误解为已经可办。E03 未确认阶段建议明确写“在线申请暂未开放，本预览不收集材料、不创建请求单”；只有真实方式核实后才显示对应入口和所需材料。

### 4.5 提交成功：按任务给持久确认

举报、申诉、补充材料成功后，不只显示会消失的“本次说明已提交”。建议在处理记录顶部保留一次性确认区：

```text
[申诉已提交]
事项编号：<真实编号>
接下来：平台会先记录首次回应；如需补充，会在通知和处理记录中提示。
[查看处理记录]
```

三类动作分别使用“举报已提交 / 申诉已提交 / 补充材料已提交”，避免把不同法律和业务含义压成“说明”。编号、回应目标和下一步必须来自真实记录；没有联系方式时不补写“联系客服”。

## 5. 命名体系

| 当前文案 | 推荐文案 | 适用位置 | 理由 |
| --- | --- | --- | --- |
| 申诉与个人信息事项 | **处理申诉**、**个人信息权益** 两个入口 | V14-C 入口拆分 | 申诉处理结论与行使个人信息权益不是同一任务 |
| 我的处理记录与帮助 | **处理记录** | V14-D 标题 | 记录是主任务；缩短后 320px 不换行 |
| 常用帮助 | **帮助与设置** | 记录页次级区域 | 当前内容包含规则和设置，并非传统问答帮助 |
| 你提交的事项有新进展 | **举报事项需要补充说明** / **申诉处理有新进展** | 通知标题 | 写明事项类型和变化，便于扫读 |
| 待补充 | **待你补充** | 状态标签 | 明确下一步由谁完成 |
| 已有结论 | **已出结论** | 状态标签 | 更自然，同时不暗示同意或通过 |
| 本次说明已提交 | **举报已提交 / 申诉已提交 / 补充材料已提交** | 成功确认 | 与用户刚完成的任务一致 |
| 提交结果核实中 | **正在确认是否提交成功** | 待核实页标题 | 直接说明不确定的事实 |
| 查询提交结果 | **重新查询提交结果** | 待核实主按钮 | 表达这是恢复动作，不是首次提交 |
| 到期与催回复提醒 | **到期和催回复提醒** | 提醒开关 | 使用自然语言连接，不用斜杠或省略 |
| 非结果类提醒 | **可关闭的提醒**，并列出范围 | 提醒说明 | “非结果类”是内部分类，不是用户语言 |
| 了解必要人工处理 | **了解个人信息权益** | E03 未确认阶段 | 不承诺尚不存在的办理方式 |
| 查看已有处理记录 | **查看我的处理记录** | 个人信息页 | “已有”没有说明是谁的记录 |

“服务/费用争议”属于 PRD F12 已确认的举报原因，本稿不删除。面向用户建议写为“服务或费用争议”；选中后就地提示：“举报用于提交违规线索，不替代订单异议或费用核对。”如果当前对象存在已确认且有权进入的订单入口，可提供次级按钮；没有真实入口时不得猜路由。

## 6. 按优先级修改

### P0：流程正确性和事实完整性

| 已观察问题 | 影响 | 修改建议 | 验收标准 |
| --- | --- | --- | --- |
| V14 ASCII 要求申诉页展示原处理对象、理由、时间；当前表单只显示通用对象卡 | 用户无法对照原理由补充事实，容易写成泛化投诉 | 在申诉表单顶部增加只读原处理摘要，并保留进入完整记录的入口 | 不离开表单即可知道申诉对象、当前结论、真实理由和结论时间；字段均来自可核实记录 |
| 提交结果待核实时，返回会进入处理记录，但记录列表没有待确认项或恢复入口 | 用户会怀疑是否提交，可能寻找其它入口或重复操作 | 把待确认提交作为独立可恢复状态，显示事项类型、发起时间和“重新查询提交结果” | 离开、返回、刷新后仍能找回；未核实前不生成成功记录，也不能再次提交同一请求 |
| 个人信息页写“人工办理”，却没有办理入口或当前不可办理说明 | 把尚未确认的能力表达成已可用 | E03 未确认时明确“在线申请暂未开放”；确认后只接入唯一真实入口、字段和期限 | 用户不会看到无法完成的行动承诺；页面不收证件、不创建假请求单 |
| 成功提交后直接进入通用“处理进度”，只靠短暂 Toast 表明发生了什么 | Toast 消失后难以区分刚提交的是举报、申诉还是补充材料 | 增加任务型持久确认，并显示编号、下一步和记录入口 | 刷新或稍后回看记录时仍能确认事务类型，不把提交等同已有结论 |

### P1：信息架构、命名和操作安全

| 已观察问题 | 修改建议 | 验收标准 |
| --- | --- | --- |
| “申诉与个人信息事项”“我的处理记录与帮助”在 320px 手机画板内换成两行，且各自混合不同任务 | 采用第 3 节方案 A，标题分别缩短为“处理记录”“个人信息权益”；申诉直接从原记录进入 | 320、375、414px 标题单行显示，返回键、标题和胶囊互不碰撞 |
| 处理记录首页先展示规则、提醒、个人信息和接单资料，记录被推到首屏下方 | 记录和用户待办前置；帮助与设置后置；接单资料移出 | 进入页面首屏先看到待处理项和最近记录，帮助入口不抢主任务 |
| 提醒设置离开弹层写“最近保存的文字草稿会保留” | 按页面生成具体说明：“上次保存的提醒设置不会改变，本次未保存的修改将丢失。” | 举报/申诉表单只说草稿，提醒页只说提醒设置，不复用错误名词 |
| 离开弹层把绿色主按钮给了“放弃修改”，安全动作“继续设置”反而是次按钮 | “继续填写/继续设置”使用主按钮；“放弃修改”使用危险文字色或次级按钮，并保持焦点默认落在安全动作 | 快速确认或键盘操作不易误放弃；危险动作不依赖红色单独表达 |
| 举报原因包含“服务/费用争议”，同时页面又提示应按原订单处理 | 保留 PRD 原因，但选中后显示分流说明；有真实订单路径时提供次级入口 | 用户知道举报与订单异议的边界，不因选择该原因误以为会自动停单、改价或退款 |
| 到期与催回复由一个开关控制，但页面没有说明两者是否必须绑定 | 在业务确认前把它列为决策项；若绑定，说明关闭会同时影响哪两类提醒；若不绑定，拆成两个开关 | 设置结果可预测，保存前后文字和真实通知策略一致 |

### P2：可扫读性、视觉和微交互

- 通知标题避免连续使用“有新进展”；优先使用“需要补充”“已出结论”“订单约定已更新”等可执行变化，正文再放对象摘要。
- 状态标签统一为“待确认 / 待你补充 / 处理中 / 已出结论”，不能把“已提交”误认为已经处理完成。
- `#7a877b` 小号辅助文字在 `#fcfbf7` 上约为 `3.64:1`。将正常可读的 11–12px 文本换成通过实测的深色语义令牌；禁用文字和纯装饰可另行处理。
- 时间、事项编号和状态使用一致的字号与间距；记录卡不需要同时用很淡的小字和大段说明增加扫描负担。
- 保留 `0.98` 左右的轻微按压反馈；Toast、弹层和固定底栏不得重叠，弹层打开时停止或收起 Toast。
- 长列表中“全部/未读/全部标为已读”继续固定在标题下方；工具栏不随列表滚动。
- 空状态保留插图与一句说明即可，不新增无事实依据的“去发布”“联系客服”等动作。
- 评审外壳的 V14-A—E 导航、演示状态和提交结果选择器只用于原型检查，不进入正式小程序页面。

## 7. 推荐流程

### 7.1 举报

```text
公开对象或订单的更多操作
  → 举报
  → 查看安全对象摘要
  → 选择原因
      ↘ 服务或费用争议：显示举报与订单异议的边界
  → 补充说明与图片
  → 提交
      ↘ 未完成：保留输入，可重试
      ↘ 结果待确认：进入可恢复的“正在确认是否提交成功”
      ↘ 成功：显示“举报已提交” + 编号 + 下一步
  → 处理记录
```

举报成功不自动暂停交易、改价、退款或认定对方违规。

### 7.2 申诉

```text
本人处理记录中的“已出结论”
  → 查看原对象、结论、理由和时间
  → 符合真实资格时显示“补充事实并申诉”
  → 表单继续保留原处理摘要
  → 提交申诉
      ↘ 未完成 / 待确认 / 成功
  → 同一处理记录查看首次回应和后续结论
```

申诉入口不从泛化首页创建空白事项；未确认资格时不显示按钮，已提交也不表示原结论撤销或权限恢复。

### 7.3 补充材料

```text
通知“举报事项需要补充说明”
  → 对应处理记录
  → 查看平台要求补充的具体内容
  → 补充说明与图片
  → “补充材料已提交”
  → 状态从“待你补充”进入“处理中”
```

补充表单必须保留“平台要求补什么”的上下文；没有明确补充要求时不显示该操作。

### 7.4 提醒设置

```text
通知中心或帮助与设置
  → 提醒设置
  → 查看每个开关的影响范围
  → 修改
      ↘ 保存：明确“提醒设置已保存”
      ↘ 未保存离开：继续设置 / 放弃修改
  → 微信订阅仍按真实能力单独授权
```

关闭可选提醒不影响交易结果、账单和必要站内记录；具体哪些提醒可关，必须与后端策略一致。

## 8. 状态与主操作矩阵

| 用户可见状态 | 必须显示 | 主操作 | 禁止误导 |
| --- | --- | --- | --- |
| 正在确认是否提交成功 | 事务类型、发起时间、不要重复提交 | 重新查询提交结果 | 不显示“已提交”记录或成功图标 |
| 已提交 | 事务类型、编号、提交时间、接下来会发生什么 | 查看处理记录 | 不写“已受理完成”或“已有结论” |
| 待你补充 | 明确缺少什么、提出时间 | 补充必要材料 | 不使用只有运营能理解的内部代码 |
| 处理中 | 最近一次进展、首次回应时间 | 查看处理进度 | 不承诺固定结案时间 |
| 已出结论 | 真实结论、理由、作出时间 | 符合资格时补充事实并申诉 | 不因有入口就宣称一定可申诉 |
| 提交未完成 | 原输入仍在、失败结果 | 检查后重试 | 不清空内容，不生成记录 |
| 在线申请暂未开放 | 当前能力边界、规则说明 | 查看规则与隐私说明 | 不写“人工办理”却不给真实路径 |

## 10. 实施后的验证方案

### 10.1 功能与状态

- 覆盖举报、申诉、补充材料的成功、未完成、待确认三种提交结果；验证同一请求不会重复建单。
- 验证待确认状态离开、返回和刷新后仍能恢复；查询成功只生成一次记录，查询失败回到原表单且内容保留。
- 验证申诉只从本人、符合资格的原记录进入；表单上下文与原记录对象、理由、时间完全一致。
- 验证待补充记录只显示必要补充入口；补充成功后进入处理中，并保留原事件时间线。
- 验证全部已读不删除通知、不改变订单或处理结果；失效通知不能恢复敏感材料。
- 验证提醒开关保存后真实生效；未保存离开才弹确认，保存后直接返回。
- 验证未登录、非本人记录和无权限对象均不可查看，错误不能通过前端路由绕过。

### 10.2 布局与交互

- 在 320、375、414px 检查无横向溢出，返回键、单行标题和小程序胶囊互不碰撞。
- 30 条通知、长处理理由、1000 字说明、9 张图片、长时间线均可滚动到底；固定底栏不遮挡最后字段和错误。
- 页面切换后应回到新页面合理起点；内部滚动和外部评审页滚动不得让关键标题或确认结果落在不可见位置。
- 弹层打开时 Toast 收起；焦点进入安全操作，Tab 不离开弹层，关闭后回到触发控件。
- 按钮、整行入口、单选、开关和图片移除保持至少 44px 推荐触控高度；按压反馈轻微，不造成布局跳动，减少动态效果下关闭缩放。

### 10.3 文案、无障碍与视觉

- 通知标题能独立说明事项类型和变化；摘要不泄露敏感信息。
- 错误摘要、字段错误和 `aria-invalid` 一致；错误不只依赖红色，已填内容不清空。
- 小号正常文本达到至少 4.5:1 对比度；焦点、状态和禁用不只依赖颜色。
- “待确认、已提交、处理中、已出结论”不互相替代；首次回应与结案始终分开。
- 举报、申诉、补充材料分别使用任务型成功文案，不再统一写“本次说明”。
- 未确认的后台字段、个人信息期限、微信授权和真实提交能力继续显示明确边界，并通过测试保证不会发起真实请求。
