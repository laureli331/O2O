# 五页精确结构与开发边界

页面展示文案集中在 [content.json](../../assets/ui/development-handoff-20261009/content.json)。名称“闲置”对应 PRD 历史“二手”，名称“接单员”对应历史“承接者”；这是显示层映射，不能据此擅改已有业务编号或存储枚举。下列 UI 编号只是交接索引，不是新 API/路由。

2026-10-11追加申请规则（维修和其它）：同一人对同一需求最多1份有效申请；选定前可修改或撤回；重复点击不新增记录。第二轮已确认说明选填最多300字及预估服务费选填、未报价显示待协商且不算正式约定；主动撤回后需求仍开放可立即重申，不设单独拒绝，两类同时接单不限量；发布者成功选人直接生效，其余申请结束并通知、不自动递补；选人前修改服务内容/区域/时间使原申请失效并通知重申。详见[申请与选人规则](../module-specs/application-rules.md)。字段校验、历史和并发提示仍待定；不把已选定的服务取消当成撤回申请。

2026-10-11追加联系规则（维修和其它需求）：选定前双方查看对方联系方式仍打码；选定成功后仅发布者和选中的接单员互看完整联系方式，其他申请者仍打码。草选或请求结果未知不是成功；服务端执行授权，不下发完整字段仅靠界面打码。详细地址发布时选填私密保存，仅向选中的接单员开放；完成/取消后联系方式重新打码并关闭接单员完整地址访问，发布者仍可管理本人地址；地址格式、联系变更/撤销与旧维修求助流程迁移仍待确认；闲置、免费目录及推广仍按原CT03。

2026-10-11追加费用规则（维修和其它需求）：协商后的费用在小程序内分项记录，在每个收费阶段开始前由双方确认；服务费和材料/配件/商品等实际支出分开，页面同时显示合计。检查若收费先确认，诊断后再确认维修/配件费用，不代表已付款或必须预付。费用第一轮8题已获用户“全A”确认：检查费/上门费归服务费并单列；双方可发起，另一方确认后生效；新增/修改约定需双方确认且确认前原版本有效；最多1份待确认方案，无回应不自动同意，可提醒或由发起方撤回；可先双方确认取消，已发生费用另议，不代表结清；支出票据/照片选填，垫付须自愿且双方事先确认是否垫付及上限。详见[费用规则](../module-specs/fee-rules.md)。录入字段、不同意及待确认方案修改方式已由第五轮确认；字段映射、阶段细则、并发和异议流程仍待讨论，具体页面尚待整理，也没有按选定稿¥--补出真实默认费用。个人收入暂不因此扩入维修和其它。

2026-10-11追加履约规则（维修和其它需求）：选人后服务内容/区域变更须双方确认，确认前原内容有效；预约选填，双方确认记录、改期也须确认；接单员提交完成、发布者确认后完成；任一方申请取消、另一方确认后取消。完成/取消无人回应均保持待确认，不自动结束，可提醒或提出异议。取消后发布者可主动重开同一需求，重新申请和选人，旧申请不恢复、服务费用历史保留。具体页面状态与验收边界见[履约与结束规则](../module-specs/fulfillment-rules.md)。

2026-10-11追加异常与评分规则（维修和其它需求）：完成/取消/异议说明必填1—500字，附件选填0—9；可不同意完成/取消并必填理由，不结束服务。两种申请可同时待确认，先确认生效的一种结束，另一种关闭留历史；运营不介入服务调解，原举报/评价申诉职责保留。新维修完成确认直接开启双方评分，其它加入既有双向三维体系，取消不新增资格，历史合法评分保留。具体并发与角色/统计字段需补，见[异常及评价规则](../module-specs/exception-rating-rules.md)。

## UI03：跑腿选人，对应 V03，发布者视角

顺序：选择接单员 → 公开需求摘要/服务费 → 阶段指示 → 候选接单员 → 费用说明 → 确定选择。

候选A示例报价12、不垫付；候选B示例报价15、愿垫付、上限50。它们只是视觉样例，不能成为实际默认报价。愿垫付/上限两枚标签同为浅绿底绿字且分开；上限不是服务费，格式小且不采用红色金额样式。

“待选择/履约中/待确认”只是摘要导航，不覆盖超期、取消、异议等真实状态，详细映射见组件合同和 PRD RUN规则。
