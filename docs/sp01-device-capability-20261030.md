# SP01 device and performance API capability check

This is preparation evidence, not a product or phone-performance pass. The isolated probe at [tools/sp01-device-probe](../tools/sp01-device-probe/README.md) performs local-only reads of system information, the current page's reported renderer, and Performance API capabilities. It does not initialize CloudBase, make network requests, or write storage.

## Reuse and source review

The existing storage diagnostic already reads a whitelisted set of device fields. I left it untouched because it is used for cloud permission investigations. This separate utility reuses that field set and adds `Page.renderer` and `wx.getPerformance()` capability reads. No third-party dependency or copied source package was needed. The installed WeChat-maintained `miniprogram-api-typings@5.2.3` is MIT-licensed and its generated declarations link to WeChat's API documentation. The declarations specify `wx.getPerformance()` from base library 2.11.0, report navigation/render/script entries such as app launch, route, first render, paint, script injection, package and resource timing, and type the page renderer as `webview | skyline`. The list has no FPS or per-frame entry. The official API URLs and exact installed declaration locations are recorded in the [JSON evidence](sp01-device-capability-20261030.json).

The official docs site could not be read by the research browser in this session. I therefore used the WeChat-maintained generated declarations as primary-source evidence, and will treat phone output as the needed runtime confirmation rather than assuming type declarations prove device behavior. The declarations also mark firstPaint and LCP unsupported on iOS, and FCP unsupported below iOS 14.5; `firstRender` is the common candidate if runtime reports it on each device.

## What this establishes

- Existing reports identify four physical devices and their selected refresh settings. The settings remain user-reported choices, not measured physical timing or FPS.
- The user supplied runtime output from four phones on 2026-10-30: OPPO PLJ110 (Android 17), iPhone XR (iOS 17.5.1), HUAWEI BON-AL00 (Android 12), and HUAWEI SEA-AL10 (Android 10). All four reported `webview`, callable `wx.getPerformance()`, a registered observer, and the same six supported types: `interaction`, `loadPackage`, `navigation`, `render`, `resource`, and `script`. None reported an FPS/frame metric. The user also checked the IDE Tools menu and reported no frame-rate tool there.
- The initial outputs showed current entries as “not provided”. Review found the old probe subscribed to only three entry types and copied its initial page snapshot. The revised probe subscribes to all types reported by each runtime and refreshes the buffer before copying. The first OPPO retest exposed a formatter defect: observer entries were normalized to `durationMs`, then summarized again while reading only `duration`. A regression test reproduced and fixed this. The next OPPO report showed durations for 14 of 20 output rows: `appLaunch` 865ms, `downloadPackage` 373ms, `evaluateScript` 5ms, and `firstRender` 129ms among the recognized rows. Six rows had no displayed duration: firstPaint/FCP/LCP (documented time points) and `route` (unexplained). That run also repeated visible type/duration patterns because the local page combined the full performance buffer and observer snapshots. The probe now uses the full buffer snapshot when it is nonempty and only falls back to observer entries otherwise. The following user-provided OPPO report, received after requesting a run with commit `7e9ba98`, contained 10 rows, with no repeated visible type/duration patterns; six rows displayed durations, including `appLaunch` 1532ms, `evaluateScript` 4ms, and `firstRender` 701ms. The output does not include a build revision, so the exact phone build is not independently confirmed. The `route` duration is still missing. The other three phones have not been rerun on the latest probe.
- The earlier device report listed the backup Huawei's base library as 3.17.4, while this latest probe output says 3.17.5. Both observations are retained and the discrepancy remains unresolved; neither sets the product support floor. The probe remains configured to 3.17.4 as the lowest earlier report, not as an approved product support floor.
- `wx.getPerformance()` has no documented FPS/per-frame entry in the WeChat-maintained API typings. No FPS, scroll-frame timing, or button-to-visible-feedback timing will be derived from first-render or navigation durations. The fresh OPPO output includes `interaction` and `render` entries with redacted names; their semantics and suitability for latency measurement remain unverified. The repeated visible patterns are absent in the latest report, but its build revision is not embedded; the `route` duration anomaly remains open.
- The installed WeChat CLI help has no dedicated performance-capture command. The user also reports no frame-rate tool in the IDE Tools menu. The WeChat Developer Tools installation includes ADB 1.0.39. The initial host check found no device; after the user connected the backup Huawei, the read-only check confirmed SEA-AL10, Android 10/API 29, build `SEA-AL10 4.0.0.121(C00E120R5P4)`. The user checked Developer Options > Debugging and did not find System Tracing. Perfetto's UI runs locally in the browser and does not upload a trace by default. Android's official jank guide describes UI-thread and RenderThread frame events for Android 10 and lower, but this has not been verified against a trace from the Huawei, the browser Perfetto UI, or the mini-program's embedded renderer. Apple's Animation Hitches tool can show frame lifetimes, but it requires Xcode/Instruments on macOS; it is unavailable in the user's Windows 11 environment, and profiling WeChat's embedded renderer is unverified.

### FPS method research (candidate only)

- [Android on-device system tracing](https://developer.android.com/topic/performance/tracing/on-device) is available on Android 9+ and can record without ADB. Android 10+ exports `.perfetto-trace` files.
- [Android UI jank detection](https://developer.android.com/studio/profile/jank-detection) documents UI-thread and RenderThread frame events in the Display section for Android 10 and lower. We have not yet verified those events on the user's device or that they isolate WeChat's embedded mini-program renderer.
- [Perfetto's system tracing guide](https://perfetto.dev/docs/getting-started/system-tracing) states its browser UI processes traces locally and does not upload them by default. Do not use the Share action for project traces.
- [Apple Animation Hitches](https://developer.apple.com/documentation/xcode/improving-app-responsiveness) provides frame-lifetime and hitch analysis through Instruments, but the user's Windows 11 setup has no macOS/Xcode, and use against WeChat's embedded mini-program remains unverified.

### Android 10 ADB candidate (command and layer output observed; QP05 method not validated)

- Android's [dumpsys documentation](https://developer.android.com/tools/dumpsys) documents `adb shell dumpsys gfxinfo <package> framestats` as a detailed recent-frame timing source. The [Slow Sessions guide](https://developer.android.com/topic/performance/issues/slow-session) documents `adb shell dumpsys SurfaceFlinger --timestats` and says its output contains per-layer `averageFPS` and present-to-present histograms. That guide is scoped to games; using it for WeChat's embedded mini-program remains a candidate until the actual foreground layer is identified and the result is checked against this project's contract.
- Android 10's [AOSP SurfaceFlinger source](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/android10-release/services/surfaceflinger/SurfaceFlinger.cpp) routes `--timestats` to TimeStats. The [TimeStats implementation](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/android10-release/services/surfaceflinger/TimeStats/TimeStats.cpp) records per-layer present-to-present deltas, and [its formatter](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/android10-release/services/surfaceflinger/TimeStats/timestatsproto/TimeStatsHelper.cpp) emits layer/package names, total/dropped frames, average FPS and histograms. This confirms the feature exists in AOSP Android 10, not that Huawei exposes it in this build.
- The AOSP histogram has neighboring 98ms and 102ms buckets. Because deltas are assigned to the next configured bucket, a nonzero 102ms bucket can include values at or below 100ms. Therefore it cannot alone prove an exact `>100ms` event; an ambiguous nonzero bucket must be resolved with exact frame timestamps or left unresolved. A zero 102ms-and-higher count may support the no-long-stall check only after layer attribution and OEM behavior are validated.
- A read-only check on the connected SEA-AL10 confirmed the foreground activity `com.tencent.mm/.plugin.appbrand.ui.AppBrandUI00`, and SurfaceFlinger listed the corresponding layer `com.tencent.mm/com.tencent.mm.plugin.appbrand.ui.AppBrandUI00#0`. The `--timestats -dump` command returned an empty result before the collection was enabled. The one temporary collection completed with start, dump, and disable exit codes 0; no app data, CloudBase resource, permission or persistent setting was changed.

#### First Huawei feasibility capture (not acceptance evidence)

- Environment: SEA-AL10, Android 10/API 29, build `SEA-AL10 4.0.0.121(C00E120R5P4)`, ADB 1.0.39; foreground WeChat activity `AppBrandUI00`.
- The dump reported `layerName = com.tencent.mm/com.tencent.mm.plugin.appbrand.ui.AppBrandUI00#0`, `packageName = com.tencent.mm`, `totalFrames = 25`, `droppedFrames = 0`, and `averageFPS = 31.250`.
- Nonzero `present2present` buckets for that layer were `16ms=23`, `82ms=1`, and `350ms=1`. The output also reported global `totalFrames=85`, `missedFrames=0`, `displayOnTime=33664ms`, `statsStart=1793348446`, and `statsEnd=1793348479`.
- The collection was intended to include one short scroll interval, but `statsStart` and `statsEnd` differ by about 33 seconds and the dump reports `displayOnTime=33664ms`, rather than establishing the requested 15-second segment. No input trace or separate user confirmation ties the frames to a continuous scroll. Therefore the 31.25 FPS and 350ms bucket cannot be attributed to a scroll segment or diagnosed as an app-render stall. This is a tool-feasibility observation, not a QP05 pass or fail.
- What is established: Huawei firmware exposed the command, and the foreground WeChat AppBrandUI00 layer returned numeric per-layer frame statistics. What remains open: synchronized segment boundaries, repeatability under frozen conditions, and whether a layer interval can be attributed to an app-render stall rather than idle/surrounding activity.

#### `gfxinfo framestats` attribution check (not acceptance evidence)

- Android's [AOSP UI performance guide](https://android.googlesource.com/platform/frameworks/base/+/562ae3a/docs/html/training/testing/performance.jd) documents `adb shell dumpsys gfxinfo <PACKAGE_NAME> framestats` as nanosecond timing rows for the most recent 120 frames and documents `... gfxinfo <PACKAGE_NAME> reset` for constraining counters to a particular animation. It describes a short collection window of about two seconds. The reset command has now been verified twice on this Huawei process; the synchronized measurement itself remains pending.
- A read-only process listing showed `com.tencent.mm:appbrand1` and `com.tencent.mm:appbrand0`. `dumpsys gfxinfo com.tencent.mm` returned the `LauncherUI` ViewRoot, so main-process results are not used for this mini-program check. `dumpsys gfxinfo com.tencent.mm:appbrand0 framestats` returned one visible ViewRoot, `com.tencent.mm/com.tencent.mm.plugin.appbrand.ui.AppBrandUI00`, matching the resumed page; appbrand1 returned no ViewRoot in that check. This attributes results to the WeChat AppBrand host window, not an isolated embedded WebView layer.
- An earlier read-only aggregate snapshot for appbrand0 showed 1070 cumulative frames, 13 janky frames (1.21%), p50/p90/p95/p99 of 5/7/10/17ms, and a ten-row recent frame sample whose longest adjacent IntendedVsync interval was 115.81ms. A later pre-reset check showed 1577 cumulative frames and 13 janky frames (0.82%). The snapshots were taken at different times and were not tied to a confirmed scroll; neither the janky percentage nor 115.81ms interval is attributed to the application or a user interaction.
- The exact reset command was run on the target process and returned exit code 0. Before the first reset, the aggregate was 3033 frames/13 janky; the post-reset query had a new `Stats since` value and 66 frames/0 janky. A later unsynchronized read showed 301 frames/0 janky. Before the controlled sample, the process was reset again; the `Stats since` value changed, and an immediate query showed 0 frames/0 janky. The reset mechanism is verified, but none of these counts represents a controlled scroll measurement.
- The first requested scroll attempt is recorded under `firstUserScrollAttempt`; the second, live-poll attempt is under `livePollScrollAttempt` in the JSON. The user confirmed a short scroll during the second 15.2-second window, but no exact gesture bounds or input timestamps were captured. The aggregate cannot establish per-scroll FPS or an app-attributed stall. A prior read-only guard found Android Display settings and avoided issuing input. The user later reopened the probe and signaled readiness; a separate synthetic swipe feasibility sample is recorded below. Any usable result must meet repeated QP05 sampling and attribution requirements. The reset affects only transient graphics diagnostic counters for this process; it does not change app data, cloud resources, permissions, network or persistent device settings.

#### Guarded synthetic swipe feasibility sample (not acceptance evidence)

- Preflight verified SEA-AL10 / Android 10, resumed `AppBrandUI00`, and its visible ViewRoot under `com.tencent.mm:appbrand0`. The transient `gfxinfo` reset returned 0. `adb shell input touchscreen swipe 540 1900 540 700 5000` completed successfully; its 5000ms duration argument was supplied, and the host-side command wall time was 5419.1ms.
- The post-run summary reported 93 total frames, 0 janky frames, and p50/p90/p95/p99 of 5/6/7/8ms. Ten recent frame-stat rows were returned; all ten had the no-input sentinel for `OldestInputEvent`, `NewestInputEvent` was zero, the maximum adjacent `IntendedVsync` gap was 33.07ms, and none of those ten gaps exceeded 100ms.
- AOSP's [`InputShellCommand`](https://android.googlesource.com/platform/frameworks/base/+/81f52b053da6/services/core/java/com/android/server/input/InputShellCommand.java) shows that this command injects synthetic DOWN/MOVE/UP motion events. The host-side wall time also includes shell/ADB overhead. More importantly, `gfxinfo` sees the AppBrand host ViewRoot, not an isolated embedded WebView compositor stream. Do not divide 93 frames by the command duration to claim FPS; the zero-janky count and percentiles also do not describe only the scroll segment.
- This confirms the guarded command reaches the visible host process and returns numeric data. It does not prove QP05 pass or fail. The next useful step is a local Android system trace that can align input with app/WebView and SurfaceFlinger frame tracks; if Android 10/Huawei cannot attribute the embedded renderer, R03 remains pending until a supported sampler is identified.
