# SP01 device and performance API capability check

This is preparation evidence, not a product or phone-performance pass. The isolated probe at [tools/sp01-device-probe](../tools/sp01-device-probe/README.md) performs local-only reads of system information, the current page's reported renderer, and Performance API capabilities. It does not initialize CloudBase, make network requests, or write storage.

## Reuse and source review

The existing storage diagnostic already reads a whitelisted set of device fields. I left it untouched because it is used for cloud permission investigations. This separate utility reuses that field set and adds `Page.renderer` and `wx.getPerformance()` capability reads. No third-party dependency or copied source package was needed. The installed WeChat-maintained `miniprogram-api-typings@5.2.3` is MIT-licensed and its generated declarations link to WeChat's API documentation. The declarations specify `wx.getPerformance()` from base library 2.11.0, report navigation/render/script entries such as app launch, route, first render, paint, script injection, package and resource timing, and type the page renderer as `webview | skyline`. The list has no FPS or per-frame entry. The official API URLs and exact installed declaration locations are recorded in the [JSON evidence](sp01-device-capability-20261030.json).

The official docs site could not be read by the research browser in this session. I therefore used the WeChat-maintained generated declarations as primary-source evidence, and will treat phone output as the needed runtime confirmation rather than assuming type declarations prove device behavior. The declarations also mark firstPaint and LCP unsupported on iOS, and FCP unsupported below iOS 14.5; `firstRender` is the common candidate if runtime reports it on each device.

## What this establishes

- Existing reports identify four physical devices and their selected refresh settings. The settings remain user-reported choices, not measured physical timing or FPS.
- The user supplied runtime output from four phones on 2026-10-30: OPPO PLJ110 (Android 17), iPhone XR (iOS 17.5.1), HUAWEI BON-AL00 (Android 12), and HUAWEI SEA-AL10 (Android 10). All four reported `webview`, callable `wx.getPerformance()`, a registered observer, and the same six supported types: `interaction`, `loadPackage`, `navigation`, `render`, `resource`, and `script`. None reported an FPS/frame metric. The user also checked the IDE Tools menu and reported no frame-rate tool there.
- The initial outputs showed current entries as “not provided”. Review found the old probe subscribed to only three entry types and copied its initial page snapshot. The revised probe subscribes to all types reported by each runtime and refreshes the buffer before copying. The first OPPO retest exposed a formatter defect: observer entries were normalized to `durationMs`, then summarized again while reading only `duration`. A regression test reproduced and fixed this. The next OPPO report showed durations for 14 of 20 output rows: `appLaunch` 865ms, `downloadPackage` 373ms, `evaluateScript` 5ms, and `firstRender` 129ms among the recognized rows. Six rows had no displayed duration: firstPaint/FCP/LCP (documented time points) and `route` (unexplained). That run also repeated visible type/duration patterns because the local page combined the full performance buffer and observer snapshots. The probe now uses the full buffer snapshot when it is nonempty and only falls back to observer entries otherwise. The following user-provided OPPO report, received after requesting a run with commit `7e9ba98`, contained 10 rows, with no repeated visible type/duration patterns; six rows displayed durations, including `appLaunch` 1532ms, `evaluateScript` 4ms, and `firstRender` 701ms. The output does not include a build revision, so the exact phone build is not independently confirmed. The `route` duration is still missing. The other three phones have not been rerun on the latest probe.
- The earlier device report listed the backup Huawei's base library as 3.17.4, while this latest probe output says 3.17.5. Both observations are retained and the discrepancy remains unresolved; neither sets the product support floor. The probe remains configured to 3.17.4 as the lowest earlier report, not as an approved product support floor.
- `wx.getPerformance()` has no documented FPS/per-frame entry in the WeChat-maintained API typings. No FPS, scroll-frame timing, or button-to-visible-feedback timing will be derived from first-render or navigation durations. The fresh OPPO output includes `interaction` and `render` entries with redacted names; their semantics and suitability for latency measurement remain unverified. The repeated visible patterns are absent in the latest report, but its build revision is not embedded; the `route` duration anomaly remains open.
- The installed WeChat CLI help has no dedicated performance-capture command. The user also reports no frame-rate tool in the IDE Tools menu. Official Android documentation identifies an on-device System Tracing candidate: Android 9+ can record without ADB, and Android 10+ saves a `.perfetto-trace`; the backup Huawei SEA-AL10 is Android 10 and selected at 60Hz. Perfetto's UI runs locally in the browser and does not upload a trace by default. Android's official jank guide describes UI-thread and RenderThread frame events for Android 10 and lower, but this has not been verified against a trace from the Huawei, the browser Perfetto UI, or the mini-program's embedded renderer. It is not yet an approved FPS method. Apple's Animation Hitches tool can show frame lifetimes, but it requires Xcode/Instruments on macOS; it is unavailable in the user's Windows 11 environment, and profiling WeChat's embedded renderer is unverified.

## Validation and next device step

Local unit coverage checks report-field allowlisting, unknown renderer handling, safe metric normalization, fresh-copy behavior, runtime-advertised type observation, normalized-duration preservation, snapshot precedence, and absence of cloud/network/storage APIs. The four phones establish renderer and API capability; the OPPO reports are not a performance pass. The user checked the IDE Tools menu and found no frame-rate item. First, test System Tracing on the Android 10/60Hz backup phone with a short scroll on the isolated probe; confirm the trace exposes attributable WeChat mini-program frame events and can support the contract's average-FPS and over-100ms-stall calculations. A trace file alone is not a pass. Then determine the iPhone sampling path and rerun the latest isolated probe on the other phones. Do not derive FPS from refresh settings or unrelated timings. Until then the minimum library, product renderer, FPS sampler, and device groups stay open.

### FPS method research (candidate only)

- [Android on-device system tracing](https://developer.android.com/topic/performance/tracing/on-device) is available on Android 9+ and can record without ADB. Android 10+ exports `.perfetto-trace` files.
- [Android UI jank detection](https://developer.android.com/studio/profile/jank-detection) documents UI-thread and RenderThread frame events in the Display section for Android 10 and lower. We have not yet verified those events on the user's device or that they isolate WeChat's embedded mini-program renderer.
- [Perfetto's system tracing guide](https://perfetto.dev/docs/getting-started/system-tracing) states its browser UI processes traces locally and does not upload them by default. Do not use the Share action for project traces.
- [Apple Animation Hitches](https://developer.apple.com/documentation/xcode/improving-app-responsiveness) provides frame-lifetime and hitch analysis through Instruments, but the user's Windows 11 setup has no macOS/Xcode, and use against WeChat's embedded mini-program remains unverified.

No cloud, user files, money, dependency installation, or formal product code are involved. Rollback is deleting the isolated local probe and reverting its scoped commit.
